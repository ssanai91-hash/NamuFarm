# 나무팜 연결 · 판매 관리 (API v5 / Room v15)

## 판매 흐름

홈페이지 견적 요청 → 앱 요청함 → 품목·가격 확인 → 공식 견적서 이메일 PDF/문자 JPG 초안 → 고객의 전화·문자 구매 결정 → 구매확정 → 입금확인 → 배송확인 → 판매완료.

이메일/MMS 초안을 여는 것으로 발송·입금·배송을 확인하지 않습니다. 운영자가 실제 입금과 배송/인수를 확인하고 각 상태 버튼을 누릅니다. 구매확정 때 재고를 차감하고 배송 전 주문취소 때 한 번 복원합니다. 배송 이후 반품·환불과 판매 완료 후 정정은 이번 상태 모델에 포함하지 않습니다. 진행/전체 주문은 ‘오늘 주문 → 전체 판매 관리 · 일/월/년 매출 조회’에서 확인합니다.

## 기기 인증과 자동 보호

판매자는 15분 유효한 일회용 연결 코드만 입력합니다. 새 견적과 주문은 고객용 RSA 키, JSON 백업, 백업 비밀번호 없이 읽고 씁니다. 연결 코드 자체는 계속 저장하는 비밀번호가 아니며, 앱/PC가 별도 256비트 기기 토큰을 생성해 서버에 등록합니다. 인증 없는 요청·판매 조회는 계속 거절합니다.

홈페이지 Worker → Apps Script는 HTTPS와 서버 전용 WEB_SECRET으로 연결합니다. v5 고객정보는 비공개 Google Sheet의 원본 JSON 및 표시 셀에 저장하므로 시트 접근 권한자는 읽을 수 있습니다. 사용자 관리 RSA로 감춘다는 보장은 제거했습니다. 시트의 링크 공개/공유 범위는 넓히지 않습니다. 판매자는 사이트가 요청하는 이름·전화뿐 아니라 메일 견적과 택배에 필요한 이메일·주소도 처리합니다.

Android Room·전송 대기는 기존 Keystore AES-GCM 보호를 유지하고 새 RSA 키를 자동 생성하지 않습니다. PC SQLite·토큰·초안·전송 대기는 AES-GCM으로 보호하고, 저장 키를 Windows 현재 사용자 DPAPI로 감쌉니다. 키 파일 입력이나 매번 비밀번호를 묻는 과정은 없습니다. PC v1 보관함은 기존 비밀번호를 한 번 확인한 후 저장 키만 다시 감싸며, 로컬 데이터와 pending UUID는 바꾸지 않습니다.

기존 v4 암호화 행과 미전송 이벤트는 삭제하거나 덮어쓰지 않습니다. 기존 키가 남아 있으면 그대로 읽습니다. 키가 없는 기기는 ‘이전 자료 복원’에서 원래 백업을 가져와야 합니다. 자료를 읽지 못하면 동기화 순번을 전진시키거나 성공으로 표시하지 않습니다. 이전 개인키가 없으면 그 암호문을 복원할 수 없습니다. 이전 자료를 위해 서버 SELLER_PUBLIC_KEY를 삭제/교체하지 마세요.

새 기기는 인증 후 서버에 동기화된 v5 자료를 다시 가져옵니다. 로컬 초안·미전송 내역은 새 기기로 자동 복구되지 않으므로 기기 변경 전 처리해야 합니다. APK 서명은 고객정보 저장 키와 별개이며 [배포 안내](SIMPLE_CONNECTION_V5.md)를 따릅니다.

## 시트와 멱등 동기화

| 시트 | 저장 내용 |
|---|---|
| 웹견적요청 또는 월별 파일의 날짜 시트 | UUID, 전체 기간 접수/변경 순번·시각, 상태, HMAC 해시, 알림 outbox, 고객정보 원본 JSON (기존 v4 암호문 호환) |
| 판매기록 | 주문번호·revision, 상태·단계 시각, 수량·매출·세액·원가·비용·매출이익, 고객/견적서 본문 (기존 v4 암호문 호환) |
| 판매변경이력 | 변경 이벤트 ID·주문번호·revision·내용 digest·서버 수신 시각 |

최신 판매 행을 주문번호로 upsert합니다. 재무 metadata와 고객 본문을 정렬 JSON으로 digest 검증하고, 고객 본문의 주문 금액·품목과 다시 비교합니다. v5는 로컬 orderId와 null 문서 필드를 해시에서 제외하여 Android·Python 간 일치를 보장합니다. 이벤트 UUID와 revision의 동일 재전송은 같은 영수증을 반환합니다. 최신 행 저장 후 변경 영수증 기록이 실패해도 다음 변경을 허용하기 전에 이전 영수증을 복구합니다. 다른 기기의 stale revision은 거절하고 pending을 보존합니다.

로컬 주문 변경과 암호화된 고정 이벤트 outbox를 한 transaction에 저장합니다. 이벤트 ID·본문·digest는 재시도마다 바꾸지 않습니다. 기존 v4 pending의 nonce/암호문도 바꾸지 않습니다. FIFO 전송 실패 시 Pull/통계 조회를 중단합니다. 새 secure sale는 기존 평문 주문/주소/취소 API로 보내지 않습니다. 기존 pending 주문은 먼저 보안 이벤트로 고정·변환한 뒤 전송합니다. 재고는 기존 API에 별도 절대 수량 outbox로 보내며, 단일 폰 기준 중복 차감을 막습니다. **여러 폰이 동시에 같은 재고의 절대 수량을 수정하는 충돌은 해결한 것으로 간주하지 않습니다.**

기존 재고·주문 API의 오래된 주문 Sheet 평문이나 다운로드 사본을 이 새 견적 서버가 자동으로 제거하지는 않습니다. 기존 시트 과거 버전·내보낸 파일·메일/MMS 수신 사본·Google 서비스 백업까지 활성 셀 삭제와 동시에 삭제됐다고 보장하지 않습니다. 기존 평문 자료와 백업의 보관 정리는 별도 확인해야 합니다.

## 보관·삭제

미구매 홈페이지 문의/연결된 견적·발행본은 접수 후 30일이 지나면 삭제합니다. 상담 종료 버튼으로 더 일찍 종료할 수 있습니다. 구매 확정 후 문의 사본을 삭제하고 실제 거래 기록·발행 견적서에 필요한 고객 정보는 따로 보관합니다. 종료된 거래의 5년 기한이 끝나면 고객 암호문·문서·직접 식별자와 변경 영수증을 제거하고 고객 이름·연락처 없는 재무 자료를 남깁니다. 장기 미완료 계약은 운영자가 종료 여부를 확인해야 합니다.

서버는 5분 간격 시간 트리거로 정리하며, 조회 시에는 30일 지난 문의를 즉시 숨깁니다. 앱은 시작 시/WorkManager(15분 요청, OS가 실행 시각 조절)로 정리합니다. 꺼진/오프라인 폰은 다음 실행 때 정리합니다. 메일·MMS 첨부 캐시는 24시간 후 앱에서 정리합니다. 앱 밖에 사용자가 저장하거나 전송한 사본은 별도 관리합니다. 삭제한 문의의 cursor/중복 방지 tombstone은 유지하여 오래된 문의가 재수신되지 않습니다.

전자상거래 관련 법령이 적용되는 계약·결제·공급 기록 5년, 불만·분쟁 기록 3년을 상세 방침에 안내합니다. 별도 민원 관리 UI와 3년 자동 파기 테이블은 이번 기능에 포함하지 않습니다. 이 앱의 거래 5년 삭제와 문의 30일 삭제를 민원 기록 시스템으로 대신 사용하지 않습니다.

## 매출·매출이익

판매완료 시각을 Asia/Seoul로 변환한 날짜로 일/월/년을 집계합니다. 구매확정·입금/배송 진행·취소 건은 매출 집계에서 제외합니다. 매출은 공급가액(선불 운반비 포함), 추가 세액은 별도입니다.

- 매입 판매: 매출 − 매입 원가 − 배송·포장 등 입력 비용.
- 판매 수수료: floor(매출 × 수수료율) − 입력 비용. 판매 방식과 비율은 주문에서 명시적으로 선택합니다.
- 원가는 재고 매입가로 미리 채우지만 운영자가 확인하기 전에는 확정 매출이익을 표시하지 않습니다. 판매 완료 전 비용 확인을 요구합니다.
- 원가 미확인 이관 기록은 매출에는 포함할 수 있으나 매출이익 합계에서 제외하고 건수를 표시합니다.
- 입력하지 않은 회사 공통 운영비·세금까지 포함한 순이익을 계산한다고 주장하지 않습니다.
