# 나무팜 암호화 · 판매 관리 (API v4 / Room v15)

## 판매 흐름

홈페이지 견적 요청 → 앱 요청함 → 품목·가격 확인 → 공식 견적서 이메일 PDF/문자 JPG 초안 → 고객의 전화·문자 구매 결정 → 구매확정 → 입금확인 → 배송확인 → 판매완료.

이메일/MMS 초안을 여는 것으로 발송·입금·배송을 확인하지 않습니다. 운영자가 실제 입금과 배송/인수를 확인하고 각 상태 버튼을 누릅니다. 구매확정 때 재고를 차감하고 배송 전 주문취소 때 한 번 복원합니다. 배송 이후 반품·환불과 판매 완료 후 정정은 이번 상태 모델에 포함하지 않습니다. 진행/전체 주문은 ‘오늘 주문 → 전체 판매 관리 · 일/월/년 매출 조회’에서 확인합니다.

## 암호화 위치와 키

홈페이지 서버(Worker)가 고객 이름·전화·선택 이메일·지역·메모·수신인과 요청 원문을 암호화한 뒤 Apps Script에 보냅니다. Apps Script는 복호화하지 않으며, 구글시트 표시 셀에도 고객정보를 넣지 않습니다. 앱에서 만든 주문의 연락처·주소·메모·견적서 원본도 앱에서 암호화해 전송합니다.

RSA 3072 OAEP SHA-256/MGF1 SHA-256으로 각 기록의 임의 AES-256 키를 감싸고, AES-GCM(12바이트 nonce/128비트 tag)으로 본문을 보호합니다. AAD는 기록 종류와 요청번호/변경 이벤트 ID에 묶습니다. 서버에는 공개키만 등록하고, 개인키는 기기 Android Keystore AES 키로 감싸 앱에 보관합니다. 개인키를 서버·GitHub·APK에 넣지 않습니다. RSA 개인키 자체를 하드웨어 Keystore에서 생성했다는 뜻은 아닙니다.

앱 Room의 고객 필드·견적서·pending payload도 기기 Keystore AES-GCM으로 저장합니다. 구 DB 평문은 transaction으로 재작성하고 WAL checkpoint/VACUUM을 수행합니다. 기기 키가 없는 일반 Android DB 자동 백업/기기 전송은 제외합니다.

## 최초 앱 연결과 기기 변경

1. 기존 서명과 실제 재고 API 환경 설정을 유지한 앱 업데이트를 설치합니다. 전용 견적 API URL은 기본 제공되며, `GOOGLE_SCRIPT_URL`/주소 검색/Firebase/계좌 정보는 실제 기존 설정을 유지해야 합니다.
2. 요청함에서 owner가 발급한 일회용 기기 연결 코드를 등록합니다.
3. ‘고객정보 보안 설정하기’에서 **12자 이상 비밀번호**로 보안 백업 JSON을 저장합니다. 파일과 비밀번호를 따로 안전하게 보관합니다.
4. ‘서버 보안 연결’을 누릅니다. 처음 등록한 공개키가 서버에 고정되며 기존 키를 다른 새 키로 덮어쓰지 않습니다.
5. 기존 RFQ 평문은 HTTPS owner 전용 암호화 bridge 응답을 확인한 뒤에만 교체합니다. 20건씩 변환하므로 ‘이전 고객 요청 변환 중’이면 서버 보안 연결을 다시 누릅니다. 실패 시 원본을 지우지 않고 고객 접수도 열지 않습니다.
6. 새 휴대폰에서는 기기 연결 후 **기존 백업을 복원**하고 서버 보안 연결을 확인합니다. 새 키를 만드는 것으로 기존 정보를 복구할 수 없습니다.

백업은 PBKDF2-HMAC-SHA1 1,300,000회(구 Android API 호환) + AES-256-GCM으로 암호화합니다. 백업 파일과 비밀번호를 모두 잃으면 복호화할 수 없습니다. 백업에는 보안키가 들어있고 고객 데이터 전체/오프라인 pending DB는 들어있지 않습니다. 폰 변경 전에 pending을 전송하고 새 기기에서 시트 기록을 가져와야 합니다. 앱 삭제 전에도 같은 주의가 필요합니다.

홈페이지는 서버 API v4, 보안키 등록·이전 데이터 변환 완료 및 상세 개인정보 안내 설정이 모두 충족될 때만 접수를 허용합니다. `QUOTE_PRIVACY_NOTICE`에는 실제 개인정보 문의 연락처를 포함한 확정 방침을 설정합니다. 어르신용 화면에는 ‘고객정보는 암호화해 보관합니다. 견적 문의는 30일이 지나면 자동 삭제하며, 구매 기록은 법에서 정한 기간 동안 보관합니다.’를 표시합니다.

## 시트와 멱등 동기화

| 시트 | 저장 내용 |
|---|---|
| 웹견적요청 또는 월별 파일의 날짜 시트 | UUID, 전체 기간 접수/변경 순번·시각, 상태, HMAC 해시, 알림 outbox, 암호화 본문 |
| 판매기록 | 주문번호·revision, 상태·단계 시각, 수량·매출·세액·원가·비용·매출이익, 암호화 고객/견적서 본문 |
| 판매변경이력 | 변경 이벤트 ID·주문번호·revision·내용 digest·서버 수신 시각 |

최신 판매 행을 주문번호로 upsert합니다. 공개 재무 metadata와 암호문을 정렬 JSON으로 digest 검증하고 앱에서 복호화한 주문과 다시 비교합니다. 이벤트 UUID와 revision의 동일 재전송은 같은 영수증을 반환합니다. 최신 행 저장 후 변경 영수증 기록이 실패해도 다음 변경을 허용하기 전에 이전 영수증을 복구합니다. 다른 기기의 stale revision은 거절하고 pending을 보존합니다.

로컬 주문 변경과 암호화된 고정 이벤트 outbox를 한 transaction에 저장합니다. nonce/암호문은 재시도마다 바꾸지 않습니다. FIFO 전송 실패 시 Pull/통계 조회를 중단합니다. 새 secure sale는 기존 평문 주문/주소/취소 API로 보내지 않습니다. 기존 pending 주문은 먼저 보안 이벤트로 고정·변환한 뒤 전송합니다. 재고는 기존 API에 별도 절대 수량 outbox로 보내며, 단일 폰 기준 중복 차감을 막습니다. **여러 폰이 동시에 같은 재고의 절대 수량을 수정하는 충돌은 해결한 것으로 간주하지 않습니다.**

기존 재고·주문 API의 오래된 주문 Sheet 평문이나 다운로드 사본을 이 새 견적 서버가 자동으로 제거하지는 않습니다. 기존 시트 과거 버전·내보낸 파일·메일/MMS 수신 사본·Google 서비스 백업까지 활성 셀 삭제와 동시에 삭제됐다고 보장하지 않습니다. 기존 평문 자료와 백업의 보관 정리는 별도 확인해야 합니다.

## 보관·삭제

미구매 홈페이지 문의/연결된 견적·발행본은 접수 후 30일이 지나면 삭제합니다. 상담 종료 버튼으로 더 일찍 종료할 수 있습니다. 구매 확정 후 문의 사본을 삭제하고 실제 거래 기록·발행 견적서에 필요한 고객 정보는 따로 보관합니다. 종료된 거래의 5년 기한이 끝나면 고객 암호문·문서·직접 식별자와 변경 영수증을 제거하고 고객 이름·연락처 없는 재무 자료를 남깁니다. 장기 미완료 계약은 운영자가 종료 여부를 확인해야 합니다.

서버는 5분 간격 시간 트리거로 정리하며, 조회 시에는 30일 지난 문의를 즉시 숨깁니다. 앱은 시작 시/WorkManager(15분 요청, OS가 실행 시각 조절)로 정리합니다. 꺼진/오프라인 폰은 다음 실행 때 정리합니다. 메일·MMS 첨부 캐시는 24시간 후 앱에서 정리합니다. 앱 밖에 사용자가 저장하거나 전송한 사본은 별도 관리합니다. 삭제한 문의의 cursor/중복 방지 tombstone은 유지하여 오래된 문의가 재수신되지 않습니다.

전자상거래 관련 법령이 적용되는 계약·결제·공급 기록 5년, 불만·분쟁 기록 3년을 상세 방침에 안내합니다. 별도 민원 관리 UI와 3년 자동 파기 테이블은 이번 기능에 포함하지 않습니다. 이 앱의 거래 5년 삭제와 문의 30일 삭제를 민원 기록 시스템으로 대신 사용하지 않습니다.

## 매출·매출이익

판매완료 시각을 Asia/Seoul로 변환한 날짜로 일/월/년을 집계합니다. 구매확정·입금/배송 진행·취소 건은 매출 집계에서 제외합니다. 매출은 공급가액(선불 운반비 포함), 추가 세액은 별도입니다.

- 매입 판매: 매출 − 매입 원가 − 배송·포장 등 입력 비용.
- 판매 수수료: floor(매출 × 수수료율) − 입력 비용. 판매 방식과 비율은 주문에서 명시적으로 선택합니다.
- 원가는 재고 매입가로 미리 채우지만 운영자가 확인하기 전에는 확정 매출이익을 표시하지 않습니다. 판매 완료 전 비용 확인을 요구합니다.
- 원가 미확인 이관 기록은 매출에는 포함할 수 있으나 매출이익 합계에서 제외하고 건수를 표시합니다.
- 입력하지 않은 회사 공통 운영비·세금까지 포함한 순이익을 계산한다고 주장하지 않습니다.

## 서버 배포와 검사

Apps Script에 `Code.gs`, `SecureCommerce.gs`, `MonthlyStorage.gs`와 manifest를 모두 넣습니다. 최신 manifest는 월별 파일 생성을 위한 고급 Drive API v3와 `drive.file` 권한을 포함하므로 활성화/재승인이 필요합니다. owner가 `setupQuoteRequests()`를 실행하면 기존 시트와 알림/삭제 트리거를 생성합니다. 기존 Sheet 데이터는 초기화하지 않습니다. 기존 웹 앱 배포를 새 버전으로 갱신해 URL과 접근 설정을 유지합니다.

월별 파일·날짜 시트·전체 접수 색인의 활성화는 별도입니다. [월별 저장 안내](MONTHLY_QUOTE_STORAGE.md)의 `setupMonthlyQuoteStorage()` → 감사 → `enableMonthlyQuoteStorage()` 순서를 따릅니다. 이전 자료는 제자리에서 계속 읽고 파기하며, 선택적인 복사 이관 후 남은 원본 사본도 파기 대상에 포함합니다.

검사: `node --test server/quote-requests/tests/*.test.cjs`, `node --test website/tests/privacy-crypto.test.mjs`, `bash gradlew testDebugUnitTest assembleDebug`. 실제 기기의 백업 파일 선택·기존 서명 업데이트·FCM·이메일/MMS 전달은 휴대폰에서 확인해야 합니다.
