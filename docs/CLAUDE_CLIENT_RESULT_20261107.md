# 나무팜 · Claude 클라이언트 구현 결과 (2026-11-07)

기준 지시: `docs/CLAUDE_NAPI_ANDROID_20261107.md` (GPT 서버 커밋 `ac2c690`). 작업 범위는 `desktop/`, `app/`이며 서버·홈페이지는 변경하지 않았다.

- 버전: **나피 0.5.16**, **Android 1.1.41 (versionCode 44)**
- 미빌드·미배포: 컴파일, 자동시험, Actions, Apps Script 재배포, 실제 접수·문자·메일 시험은 하지 않았다.
- 정적 확인만 했다: Python 문법·이름 검사(pyflakes, 기존 경고 외 신규 없음), Kotlin 괄호 균형.
- Android DB 스키마는 바꾸지 않았다. `NamuFarmQuotes.db` v1 그대로이며, DAO 조회 1개만 추가했다. 패키지·서명도 그대로다.

## 공통 동작

- 공유 기능 사용 조건: 서버 공개정보에 `confirmedQuoteVersion:1`, `confirmedQuotePayment:1`이 있고 운영 방식이 `annual-two-tabs`여야 한다(나피). Android는 서버가 `get_confirmed_quote`를 지원할 때만 쓴다.
- 서버를 재배포하기 전에는 두 앱 모두 기존 동작을 그대로 유지한다.
- 수정·발송·입금 작업 ID는 네트워크 전에 먼저 로컬에 저장한다. 응답이 끊기면 같은 ID와 같은 본문으로 다시 확인한다. `CONFLICT`가 오면 자동으로 덮어쓰지 않는다.
- 서버 버전 번호와 지문은 서버 응답 값을 그대로 저장한다. 로컬에서 계산한 비교 키(내용 키)는 서버 지문과 별도로 둔다.
- 견적 연결은 웹 접수 UUID(`sourceRequestId`)로만 한다. 서버 원본이 없는 수기견적은 서버에 올리지 않는다.

## 나피 0.5.16

- **변경 확인**
  - 실행 중 1분마다 `sync_head`만 조회한다. 작업 중에는 중첩 실행하지 않는다.
  - 요청 순번이 바뀌었을 때만 `list_requests(snapshot:false)` 증분을 받아 UUID 기준으로 병합한다. 병합과 커서 저장은 한 SQLite 트랜잭션이다(`Vault.merge_requests`).
  - 하루 1회와 수동 동기화는 기존 전체 스냅샷을 쓴다.
  - head 값은 커서로 저장하지 않는다. 같은 값이 계속 앞서면 10분마다만 재확인한다.
  - 변경이 없으면 화면을 다시 그리지 않는다.
- **확정견적 인계**
  - 전체·증분 동기화 모두 확정 상태 행을 보관한다. 이전에는 `신규`만 보관했다.
  - 다른 기기에서 확정한 견적은 기존 `new_draft` 변환에 서버 `quoteDetails`를 적용해 확정목록에 추가한다.
  - 다른 기기 품목은 원가를 확인할 수 없어 `costConfirmed=false`로 둔다.
  - PC에서 삭제한 확정견적은 다시 가져오지 않는다(`dismissed_server_quotes`).
- **버전 연결과 선택**
  - 내용이 같으면 서버 버전과 연결만 한다.
  - 이 PC에서 바뀐 것이 없고 서버 버전이 더 새로우면 서버 내용을 적용한다.
  - 둘 다 다르면 목록에 ‘서버 확인 필요’를 표시하고, 열 때 ‘서버 내용 사용 / 이 PC 수정본 저장’을 묻는다.
  - 선택하지 않은 사본은 `quote_conflict_archive`와 보관함 백업에 남긴다.
- **수정과 견적완료**: 연결된 웹 견적의 내용·요청사항을 저장하면 `revise_confirmed_quote`로 서버에 새 버전을 만든다. 기존 `quote_write_pending` 저널을 재사용한다. 원가만 바꾸면 로컬에만 저장한다.
- **발송**
  - 보내기 직전에 서버 버전을 현재 내용과 맞춘다. 그래서 새 요청은 이 시점에 `견적확정`으로 바뀐다.
  - 이어서 `reserve_quote_delivery(mode:server)`를 호출한 뒤, 기존 문자·메일에 `deliveryId`, `expectedRevision`, `quoteFingerprint`를 붙여 보낸다.
  - 서버가 발송 전에 거절하면 예약을 취소한다. 발송 기록이 없다고 확인된 경우(`found:false`)에도 예약만 취소하고 다시 보내지 않는다.
  - 문자 최종 결과 확인에는 `requestId`, `deliveryId`, `messageId`를 함께 보낸다.
  - 공유 견적은 견적의 고객 전화번호로만 보낼 수 있다.
- **입금확인**
  - 입금 문자를 보내기 전에 서버를 확인한다. 이미 다른 기기에서 입금확인했거나, 수정 후 미발송이거나, 금액이 다르면 중단한다.
  - 판매를 등록하기 전에 `confirm_quote_payment`로 서버에 선점한다. 선점 저널(`payment_claims`)에 주문번호를 고정해, 날짜가 바뀌어도 같은 번호를 쓴다.
  - `save_sale`에는 `expectedRevision`, `quoteFingerprint`를 붙인다.
  - 공유 견적의 입금확인 문자는 견적 발송이 아니므로 `requestId` 없이 보낸다.
- **기타**: 서버 공개정보에서 발신메일 항목이 빠져도 메일 기능이 막히지 않도록 했다.

## Android 1.1.41

- **트랜잭션**: 매매 주문 확정의 `insertOrder`, 견적 삭제, 로컬 재고 차감, 전송대기 등록을 한 Room `withTransaction`으로 묶었다.
- **변경 확인**
  - 앱 실행·복귀(`onResume`) 때 `sync_head`만 조회한다. 바뀌었으면 가장 최근 행 이후의 증분만 받아 병합한다. 읽음 표시는 유지하고, 오래된 응답이 새 행을 덮지 않는다.
  - 하루 1회와 동기화 버튼은 기존 스냅샷을 쓴다.
  - 쓰기 직전의 최신 확인(`latestRequest`)도 전체 스냅샷 대신 증분으로 바꿨다.
  - 백그라운드 1분 확인은 추가하지 않았다.
- **서버 버전 보관**: 기존 `quotePricingJson` 칸에 `quoteVersion`을 함께 넣는다. 가격만 읽는 기존 코드는 이 항목을 무시한다.
- **확정견적**
  - 동기화 후 로컬 기록과 서버 버전을 네트워크 없이 연결한다. 이 휴대폰에서 바뀐 것이 없으면 다른 기기의 새 버전을 적용한다.
  - 둘 다 다르면 견적을 열 때 ‘서버 내용 사용 / 이 휴대폰 수정본 저장’을 묻는다. 버린 사본은 기록 안에 보관한다.
  - 내용 수정은 서버에 새 버전으로 저장된다. ‘이 휴대폰에만 저장’ 안내는 공유 견적에서 바뀐 문구로 표시된다.
- **외부 문자·메일 앱 발송**
  - 문자·메일 앱을 열기 전에 서버 버전을 맞추고 `reserve_quote_delivery(mode:external)`를 호출한다. 이때 실제 보낼 글의 SHA-256을 함께 보낸다.
  - 기존 ‘고객에게 보냈나요?’에서 ‘견적완료’를 누를 때만 `confirm_quote_delivery`를 호출한다.
  - ‘아직 안 보냈어요’ 버튼을 눌렀을 때만 예약을 취소한다. 시트를 밀어서 닫으면 취소하지 않는다.
  - 예약한 새 요청은 답할 때까지 견적요청 탭에 남는다.
  - PDF처럼 앱 밖에서 공유한 경우는 ‘보냈어요’ 확인 시점에 예약과 확인을 함께 한다.
- **입금확인 (신규 버튼)**
  - 공유 웹 견적에 ‘입금확인’ 버튼을 추가했다. 서버 확인 → 저널(주문번호·작업 ID) 저장 → `confirm_quote_payment` → 같은 주문번호로 매매 주문(`ORDER_날짜_순번`)을 만든다. 주문 생성과 전송대기 등록은 한 트랜잭션이다.
  - 응답이 끊기거나 앱이 종료되어도 같은 주문으로 마무리하며, 주문이 두 번 생기지 않는다. 재고 차감은 하지 않는다.
  - 이미 다른 기기에서 입금확인한 견적이면 그 주문번호를 보여주고 멈춘다.
- 이전 서버나 이전 기록에서는 기존 경로를 그대로 쓴다. 새 기록 항목은 모두 null 허용이라 이전 기록도 그대로 읽힌다.

## 남은 일·제약 (후속)

- Android 판매 서버 업로드(SyncManager)는 여전히 미연결이다. 이번에는 서버 입금 선점과 공통 주문번호만 남긴다.
- FCM 수신부, 신규 기기 일회용 코드, 만료 행 물리 삭제, 사업자 설정 분리는 하지 않았다.
- Android 주문번호 `ORDER_날짜_순번`은 휴대폰마다 따로 매긴다. 여러 휴대폰이 같은 번호를 쓰면 서버가 `CONFLICT`로 막는다. 이 경우 같은 작업으로 다시 시도해도 해결되지 않으므로 사용자 확인이 필요하다.
- 기존 나피 `desktop/tests`와 Android 단위시험은 실행하지 않았다. 동기화 동작이 바뀌어 기존 가짜 API 시험의 수정이 필요할 수 있다. Android `ConfirmedQuoteRevisionTest`는 suspend 변경에 맞게 호출 방식만 고쳤다.

## 사용자 확인 항목

순서: 두 앱을 설치한다 → 발송·입금 작업을 잠시 멈춘다 → 기존 배포 ID로 서버를 반영한다.

1. 휴대폰에서 확정한 웹 견적이 나피 확정목록에 나오고, 금액·전화·요청사항이 같은지
2. 휴대폰에서 수정한 뒤 나피 동기화 시 금액·전화가 바뀌는지. 반대 방향도 같은지
3. 두 기기에서 동시에 수정할 때 선택창이 나오고, 선택하지 않은 쪽이 사라지지 않는지
4. 수정 후 미발송 상태에서 입금확인이 막히는지
5. 같은 견적을 두 기기에서 동시에 보내려 할 때 ‘다른 기기에서 발송 처리 중’이 나오는지. ‘아직 안 보냈어요’ 후 다른 기기에서 보낼 수 있는지
6. 휴대폰에서 입금확인한 견적을 나피에서 다시 입금확인하면 막히는지(주문번호 표시)
7. 응답이 끊긴 뒤 다시 눌렀을 때 같은 주문번호로 마무리되는지
8. 기존 확정견적 엑셀·나피 DB·Android DB·발송 이력·전송대기가 업데이트 후에도 그대로인지
9. 나피 1분 변경 확인 시 화면 선택이 유지되는지. 휴대폰을 다시 켰을 때 새 견적이 반영되는지
