# NamuFarm Architecture

## 1. 프로그램이 해결하려는 업무

NamuFarm의 핵심은 단순 재고 앱이 아니라 다음 업무 흐름을 끊기지 않게 연결하는 것입니다.

```
농원/묘목 마스터
      ↓
재고 등록 및 수정
      ↓
판매용 재고 조회
      ↓
견적 작성
      ↓
주문 확정
      ↓
재고 차감
      ↓
배송정보 관리
      ↓
입금확인 / 주문취소
```

현장에서는 네트워크가 항상 안정적이지 않을 수 있으므로 **폰의 Room DB가 작업 중 기준 데이터**가 되고,
Google Sheets는 원격 공유/백업 및 수동 동기화 대상이 됩니다.

---

## 2. 데이터 계층

### Room

주요 테이블:

- `farm_info`: 농원 마스터
- `species`: 묘목 마스터
- `farm_inventory`: 농원/묘목/규격별 재고
- `quote_list`: 견적
- `order_list`: 주문
- `pending_sync`: 원격 전송 대기 작업

### 원격

Android → Retrofit → Google Apps Script → Google Sheets

Google Sheet는 현재 다음 범주의 데이터를 다룹니다.

- 농원
- 묘목
- 재고
- 주문
- 주문취소
- 배송정보

---

## 3. Local-first 동기화 규칙

### Push

데이터 변경 시:

1. 로컬 DB 저장/수정
2. `pending_sync` 등록
3. 서버 전송 즉시 시도
4. 성공하면 pending 삭제
5. 실패하면 pending 유지

따라서 인터넷이 끊겨도 로컬 업무는 계속 진행할 수 있습니다.

### 전체 동기화

전체 동기화 버튼은:

1. pending 재전송
2. 하나라도 실패하면 Pull 중지
3. 재고 Pull
4. 주문 Pull
5. 로컬 화면 상태 갱신

이 순서를 지켜 **아직 서버에 못 보낸 로컬 변경을 Pull이 덮어쓰는 상황**을 피합니다.

### 농원 / 묘목 마스터

농원과 묘목은 일반 재고/주문 Pull과 분리합니다.

마스터 Pull 시 로컬 테이블 전체를 지우지 않고 원격 항목을 upsert 합니다.
오프라인에서 생성된 로컬 pending 마스터를 보호하기 위한 정책입니다.

### 재고

재고 Pull은 서버 재고를 현재 스냅샷으로 봅니다.
단, 재고 Pull 과정에서 없는 농원/묘목을 임의로 만들지 않습니다.

마스터가 없으면 해당 재고행은 스킵하고 농원/묘목 마스터 동기화가 먼저 필요합니다.

### 주문

기존 로컬 주문을 원격 주문으로 통째로 삭제/재삽입하지 않습니다.

같은 주문번호가 이미 로컬에 있으면:

- 로컬 `item_summary`
- 선불 여부 / 배송비
- 구조화된 주소

를 보존하면서 서버에서 안전하게 가져올 수 있는 상태/기본정보만 병합합니다.

---

## 4. 주문 업무 규칙

현재 지원 상태:

- `입금확인`
- `주문취소`

주문은 기록 보존이 중요하므로 영구삭제를 업무 규칙에서 제외합니다.

현재 UI에 남아 있는 영구삭제 버튼/문구는 UI 정리 단계에서 제거할 예정이며,
ViewModel의 영구삭제 진입점은 실제 데이터를 삭제하지 않도록 막아 두었습니다.

---

## 5. Room 마이그레이션

현재 DB 버전은 12입니다.

기존 코드에는 v10/v11 → v12 정식 마이그레이션 없이 destructive fallback이 있어
업그레이드 시 로컬 데이터가 초기화될 위험이 있었습니다.

현재는:

- v10 → v12
- v11 → v12

데이터 보존 마이그레이션을 제공하고 destructive fallback을 사용하지 않습니다.

향후 DB 필드를 변경할 때는 반드시:

1. Entity 수정
2. DB version 증가
3. Migration 작성
4. 기존 DB 업그레이드 테스트

를 한 세트로 처리해야 합니다.

## 6. 아직 해결해야 할 핵심 과제

### A. 주문 업로드 idempotency — 최우선

주문 업로드 후 서버 처리는 끝났지만 앱이 응답을 받기 전에 타임아웃되면
pending retry가 같은 주문을 다시 올릴 수 있습니다.

서버에서 `order_number`를 기준으로:

- 이미 존재하면 새 행 append 금지
- 재고도 두 번 차감 금지

하도록 Apps Script를 idempotent하게 만들어야 합니다.

### B. 주문 데이터 완전 왕복

현재 Sheet는 사람이 보기 좋은 주문상세 문자열을 저장하는 반면,
앱은 파이프 구분 원본 주문상세를 사용합니다.

또한 다음 정보가 Sheet 왕복 규격에 완전히 포함되지 않습니다.

- `is_prepaid`
- `shipping_fee`
- `zip_no`
- `road_address`
- `detail_address`

다른 폰에서 주문을 완전히 복원하려면 Apps Script/Sheet 스키마를 확장해야 합니다.

### C. 주문취소 시 재고 복원 정책

현재 주문확정 시 재고는 차감되지만 주문취소는 상태만 변경합니다.

업무상 주문취소 시 재고를 자동 복원할지,
이미 별도 처리된 재고일 수 있으므로 수동 복원할지 결정이 필요합니다.

이 결정 전에는 자동 복원을 구현하지 않습니다.

### D. 다중 기기

현재 농원/묘목 ID는 로컬 정수 자동증가이고 주문번호도 기기 로컬 순번에 의존합니다.

여러 스마트폰에서 동시에 신규 데이터를 만들면 충돌 가능성이 있습니다.

다중 기기까지 목표로 한다면 다음 단계에서:

- 서버 발급 ID 또는 UUID
- 주문번호 전역 유일성
- 충돌 정책

이 필요합니다.

### E. ViewModel 비대화

`ManagementViewModel`에 재고, 견적, 주문, 주소검색, 통화기록, 동기화 로직이 모두 모여 있습니다.

기능 안정화 후 다음 구조로 분리하는 것이 좋습니다.

```
UI
 ↓
ViewModel
 ↓
NamuFarmRepository
 ├─ LocalDataSource (Room)
 └─ RemoteDataSource / SyncManager
```

UI 단계 전에 데이터 안정성을 먼저 확보하고,
UI 정리와 함께 ViewModel 분리를 진행하는 것이 안전합니다.

### F. 통화 권한

`READ_CALL_LOG`, `READ_PHONE_STATE`는 민감 권한입니다.
사내용/직접 설치 앱이면 현재 목적과 맞지만,
Google Play 배포를 목표로 할 경우 정책 검토가 필요합니다.
