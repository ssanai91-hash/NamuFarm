# 만료 견적 누적 정리 · 4단계 설계안

작성일: 2026-11-17. 분석 기준 main `13cd012033e5afed3963468064b681fbd017616c`.

**현황 분석·구현 전 설계 보고만 완료했다. 구현 승인 대기다.** 앱·나피·서버 실행 코드, 업무 데이터, 시트는 변경하지 않았다. 운영 API/시트 조회·정리 실행·컴파일·자동시험·Actions·배포·문자/메일 시험도 하지 않았다.

## 3. 실제 행 정리와 남길 최소 정보

- 기존 견적 연도 파일의 `견적요청/견적확정` 두 탭과 18열, 주문 장부·판매번호·서버 URL/배포 ID는 유지한다.
- 기존 운영 관리 장부에 내부용 **견적종료색인**을 추가하는 안이다. 견적 파일에 제3의 업무 탭을 추가하지 않는다.
- 색인에는 UUID, 최초 내용지문, 접수시각(UTC/한국), 기존 접수번호, 마지막 변경순번, 종료구분(자연 만료/명시 삭제), 종료시각, 원래 연도/탭, 정리 단계만 둔다. 이름·전화·주소·품목 원문·요청사항·공식견적서 원문은 옮기지 않는다.
- `주문견적연결`, 판매번호 예약/연결, 판매 변경·삭제 이력, 판매/주문 원문, 고객문의는 정리 대상에서 제외한다. 기존 중복 방지 식별 정보의 유지 정책도 임의 축소하지 않는다.
- 새 접수의 UUID 중복 검사는 유효 행과 종료 색인을 모두 본다. 같은 UUID+같은 지문은 기존 접수 정체성을 유지하며 새 접수로 만들지 않는다. 다른 지문은 CONFLICT다. 전체 종료 색인을 매 API 응답에 싣지 않고 UUID 단건/배치 조회에만 사용한다.
- 기존 API의 만료 기록 조회와 연결 확인은 색인의 최소 표식으로 계속 가능해야 한다. 과거 종료 처리로 이미 사라진 견적 가격·입금 증거는 새로 만들어내지 않는다. 필요한 근거가 없으면 기존 같은 번호/작업을 보관하고 확인 대상으로 둔다.
- 비어 있는 행만 없애는 압축은 별도 중복 방지 색인 없이 가능하지만, **행 전체 삭제는 A:R 밖의 사용자 값·수식·메모·보호 범위까지 영향을 준다.** 후보 행의 전체 구조를 확인해 사용자 자료가 있거나 구조를 판정할 수 없으면 건너뛰고 보고한다. 메모 탭·헤더·서식·고정 행·열은 보존한다.

### 중단·중복 실행에 안전한 순서

1. 최초 활성화 전 소유자용 정리 계획에서 연도/탭별 대상·보존·건너뜀 건수를 확인하고 기존 백업 절차를 사용한다. 앱/에이전트가 운영 시트를 직접 지우지 않는다.
2. 기존 ScriptLock 안에서 종료 UUID·지문·접수번호·순번을 색인에 먼저 기록한다. 동일 UUID의 기존 색인과 내용이 다르면 중단한다.
3. 색인을 재조회해 일치함을 확인하고 정리 단계 VERIFIED를 남긴다. 검증 전 원본 삭제 금지다.
4. 원본은 **현재 UUID로 다시 확인**한다. 예전에 기억한 행 번호로 삭제하지 않는다. 검증된 연속 구간을 아래에서 위로 소량씩 삭제한다.
5. 시간/건수 예산에 도달하면 정상 중단하고 다음 실행에서 이어간다. 색인만 기록되거나 사본이 둘 다 남아도 동일 UUID로 한 건만 취급한다.
6. 실제 빈 행도 알려진 업무 범위에서만 압축한다. LAST_SEQUENCE와 일별 접수번호 카운터를 내리거나 재사용하지 않는다.

정리용 함수는 소유자 내부 유지보수로 두고, **기본 비활성화**한다. 공개 접수 경로에 정리/삭제 실행을 추가하지 않는다. 기존 트리거를 임의로 새로 만들거나 교체하지 않는다.

## 4. 수신 계약 보완 — 과거 종료 행을 일반 전체 목록에서 제외

기존 v1 응답을 조용히 바꾸지 않는다. 같은 Apps Script endpoint/인증 아래 새 클라이언트가 `quoteSyncVersion:2`를 요청하는 호환 확장안을 사용한다.

| 응답/동작 | 설계 |
| --- | --- |
| 전체 snapshot | **유효한 견적만** 포함. 기존 총건수는 선택한 응답 범위의 건수임을 명시하고 snapshotId·watermark·스키마 세대를 고정 |
| 증분 수신 | 유효 행 변경과 최근 종료 표식을 합쳐 UUID별 최신 변경을 순번대로 반환. 종료 표식 응답 구간은 기본 제안 90일이며 고객 원문 보관기간 30일을 늘리지 않음 |
| 너무 오래된 커서 | 최근 종료 구간보다 이전이면 `requiresSnapshot`/최소 유효 순번을 반환. 일부 결과를 정상 증분처럼 주지 않고 전체 재수신으로 전환 |
| 종료 판정 조회 | 인증된 UUID 배치 상태 조회를 추가. active/expired/admin_deleted/unknown을 구분하고 고객 원문을 반환하지 않음. 후보 배치 크기는 50개 |
| v1 클라이언트 | 필요하면 색인에서 기존 최소 표식을 재구성해 기존 의미를 유지. 과거의 10,000건/100페이지 제한까지 자동 개선되는 것은 아니므로 새 클라이언트 갱신이 필요 |
| 명시 삭제 | 이미 만료/색인화한 UUID라도 관리자 삭제를 새 deleted 표식·순번으로 기록. 자연 만료와 동일하게 취급하지 않음 |

- 유효한 견적 자체가 10,000건을 넘을 수도 있다. 따라서 만료 행 필터만 추가하거나 상한 숫자만 크게 바꾸지 않는다.
- 응답의 버전·범위·snapshotId·watermark·총건수·순번·중복 UUID를 끝까지 검사한다. 중간 BUSY/내용 변경이면 기존 정상 캐시와 이력을 유지하고 새 스냅샷으로 재시작한다.
- Android/PC가 가진 **웹 UUID가 있는 확정/발송/미완료 기록**은 상태 배치 조회로 명시 삭제 여부를 확인한다. 오래된 관리자 삭제도 놓치지 않으며 전체 삭제 ID를 매번 내려받지 않는다.
- 자연 만료/unknown/전체 목록에 없음만으로 로컬 확정이력·초안·발송 증거·미전송 작업을 지우거나 현재 확정 목록에서 자동 제외하지 않는다. 명시 삭제 증거와 로컬 미완료 작업이 충돌하면 보관/확인을 우선한다.
- 일부 상태 확인 실패도 성공으로 숨기지 않는다. 삭제 반영 중 종료됐다면 확실한 삭제 근거와 남은 처리를 영속화해 다시 적용하고, 확인 전에 커서만 전진하지 않는다.

## 5. 클라이언트 상한·커서 처리

### Android

- `total <= 10000`과 누적 `repeat(100)`를 종료 판정으로 쓰지 않는다. hasMore·고정 total·watermark의 **완료 조건**과 단위 실행의 시간/페이지 예산을 분리한다.
- 기존 업무 DB 3개의 이름·버전·테이블은 유지한다. 별도의 앱 내부 **임시 수신 캐시(SQLite 파일)**에 행·UUID 유일성·수신 순번·snapshotId·진행 위치를 저장하는 안이다. 이는 업무 DB가 아니며 백업/업무 조회에 섞지 않는다.
- 한 번에 몇 페이지씩 받아도 총건수의 영구 상한으로 삼지 않는다. 중단 시 “N/총건수 수신·이어받기”로 표시하고 다음 수동 동기화에서 계속한다. 전체를 메모리에 쌓지 않는다.
- 마지막 페이지/총건수/상태 배치 확인이 완료된 뒤에만 기존 Room 요청 캐시를 트랜잭션으로 교체한다. 로컬 읽음 표시와 복호화 대기·확정 이력은 기존 규칙대로 보존한다.
- 확정된 서버 watermark를 **목록의 MAX(sequence)와 독립된 커서**로 저장한다. 빈 목록이어도 다시 0부터 읽지 않는다. Room 반영 → 커서 저장 순서라서 중단되면 안전하게 같은 페이지를 재확인한다.
- 커서는 기존 수동 백업에 포함되는 NamuFarmPrefs의 버전 있는 키로 저장하고 복원한 요청 캐시와 연결을 검사한다. 현재 quote_sync_v1은 수동 백업 목록에 없어 그대로 새 영구 커서 저장소로 사용하지 않는다.
- 임시 캐시는 캐시 삭제/백업 복원/토큰 만료 때 버리고 전체를 재시작할 수 있어야 한다. 완성 전 업무 캐시는 유지하고 수신 원문의 임시 파일도 완료/실패/오래된 세션 정리 시 제거한다.

### PC 나피

- requests 경로의 `for range(100)`를 누적 총량 제한으로 쓰지 않는다. 같은 토큰·순번 진행을 검증하며 완료까지 이어받는다. 이번 변경을 판매자료 페이징 재설계로 넓히지 않는다.
- 기존 vault 업무 DB 스키마는 유지하고, 기존 암호화 방식을 재사용한 임시 수신 영역에 페이지를 보관한다. 임시 수신물이 실제 requests/sales/outbox 캐시와 섞이지 않도록 별도 임시 파일로 격리한다.
- 전체 완료 전 기존 캐시·확정 엑셀을 교체하지 않는다. 완료 뒤 watermark와 요청 캐시를 같이 반영한다. 자연 만료와 관리자 삭제를 별도 집합으로 전달한다.
- `_merge_server_quotes(authoritative=True)`의 단순 “서버 목록에 없음” 제외 규칙은 v2에서 사용하지 않는다. 자연 만료만으로 로컬 확정견적이 목록에서 사라지지 않게 한다.
- 구현 시 최신 나피 버전에서 패치 +0.0.1을 패키지·표시 버전에 함께 적용한다. **이번 문서 작성에서는 나피 코드를 고치거나 버전을 올리지 않는다.**

단위 처리의 메모리/시간/디스크 예산은 유지한다. “상한에 걸려 끝없이 실패”를 없애는 것이며 무제한 용량이나 실행시간을 보장하는 안은 아니다.

## 6. 승인 후 예상 변경 범위

| 영역 | 예상 파일/역할 |
| --- | --- |
| 서버 | TwoTabQuotes.gs, SecureCommerce.gs, Code.gs, ServerMaintenance.gs, 필요 시 종료 색인/수신 도우미 신규 파일. 레거시/월별 모드의 무단 전환 없음 |
| Android | InitialQuoteConnection.kt, WebQuoteApi.kt, 관련 DAO 조회, 임시 수신/커서 도우미, 필요 시 확정 삭제 통지 처리. 업무 DB 스키마·패키지·서명 불변 |
| PC | service.py, quote_versions.py, store.py의 수신 반영 도우미, 임시 수신 처리, 버전 두 파일 |
| 문서 | 통합 시트 스키마, 운영 절차, 현황 문서. 종료 색인의 실제 열 정의와 v2 계약을 구현 내용에 맞춰 갱신 |

판매/입금확인 잠금·주문 연결·접수 제한·발송 멱등·홈페이지 UI는 변경 대상이 아니다. 5단계 리뷰 문서와 6단계 clasp/자동 배포는 이 단계에 넣지 않는다.

## 7. 운영 반영 순서와 남은 위험

1. 호환 v2 서버 기능과 읽기 경로를 준비하되 **물리 정리는 OFF**로 둔다.
2. 같은 기존 배포 ID/URL로 서버를 반영하고 Android·PC 새 수신기를 준비한다. 실제 게시/빌드/배포는 별도 요청 전 실행하지 않는다.
3. 사용자가 빈 목록·10,000건 초과·오래 오프라인·자연 만료/관리자 삭제·중단 복구를 직접 확인한다. 도구가 운영 고객자료로 자체 시험하지 않는다.
4. 확인 후 소유자용 정리 계획/백업/활성화 절차로 VERIFIED 대상만 소량씩 물리 정리한다. 단순 코드 배포만으로 운영 행 삭제를 시작하지 않는다.

**이번 문서 커밋:** 운영 서버 재배포 불필요, 앱·나피 버전 변경 없음, 홈페이지 게시 없음.

**승인 후 구현:** 서버 코드 변경이 포함돼 기존 배포 ID의 새 버전 반영이 필요하다. 물리 정리 활성화는 별도 절차다. 구 앱/구 PC의 수신 상한은 새 버전으로 갱신해야 해결된다. 스냅샷이 자주 바뀌거나 데이터가 매우 크면 서버 제한·대기 시간이 남을 수 있고, 임시 수신 용량·중단/복원 호환성은 사용자 확인 대상이다.

실제 운영 만료 건수·행 수·서버 배포 버전·정리 트리거는 이번에 조회하지 않았다. 설계와 소스 근거만으로 운영 정상 동작을 검증했다고 주장하지 않는다.

## 8. 승인할 결정

- 최소 종료 색인을 기존 운영 장부에 추가하고, 검증 후 종료/빈 행을 물리 정리한다.
- v2 유효 견적 전용 수신 + 오래된 커서 전체 재수신 + 로컬 보관 UUID의 삭제 상태 조회를 도입한다.
- 기존 업무 DB는 유지하며 임시 수신 영역과 독립 커서로 누적 상한을 제거한다.
- 자연 만료로 로컬 확정 이력을 숨기지 않고 명시 삭제와 구분한다.
- 서버 호환 배포/클라이언트 갱신 뒤 물리 정리를 기본 OFF에서 소유자가 활성화한다.

이 설계를 보고한 뒤 **4단계 구현 승인 전 멈춘다.**
