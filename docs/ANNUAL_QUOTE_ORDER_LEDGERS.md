# 연도별 견적·주문 장부

## 확정된 운영 방식

- `나무팜_견적_2026`: `01월` ~ `12월`, 홈페이지 견적 **접수월(한국 시간)** 기준.
- `나무팜_주문_2026`: `01월` ~ `12월`, 로컬에서 최초 **입금확인한 월(한국 시간)** 기준.
- 필요한 연도의 파일을 자동 생성한다. 주문 업로드가 다음 달이나 다음 해로 늦어져도 최초 입금확인시각을 사용한다.
- 입금·배송 처리는 견적 행을 변경하지 않는다. 발송한 견적은 `견적발송완료`로 남고 주문은 별도 장부에서 관리한다.
- 배송일이 달라져도 기존 주문 행을 갱신한다. 주문번호로 찾아 갱신하므로 행 정렬 후에도 같은 주문을 수정한다.
- PC의 기존 판매·배송 화면과 동기화 버튼은 그대로 사용한다. 전화 견적은 기존 로컬 작성 방식을 유지하며, 입금확인 시 같은 주문 장부로 업로드한다.

예: 10월 접수 → 11월 입금확인 → 12월 배송완료이면 견적은 견적 파일의 10월 탭, 주문·배송은 주문 파일의 11월 탭에 남는다.

## 운영 서버 적용

코드 커밋과 실제 Apps Script 배포·초기화는 별개다. 아래 초기화는 소유자가 Apps Script 편집기에서 실행하며 공개 API로 제공하지 않는다.

1. 현재 운영 Apps Script 프로젝트의 `Code.gs`, `SecureCommerce.gs`, `MonthlyStorage.gs`, `RecoverySetup.gs`를 이 커밋 버전으로 맞추고 **`AnnualLedgers.gs`를 추가**한다. 기존 `appsscript.json`의 Sheets·Drive 권한과 Drive v3 고급 서비스를 유지한다. 실제 연결키나 운영 Script Properties는 변경하지 않는다.
2. 기존 관리 스프레드시트와 Script Properties를 백업하고, 접수/동기화를 잠시 사용하지 않는 작업 구간에서 진행한다. 기존 배포 버전이 새 색인을 모르는 상태로 동시에 접근하지 않도록 먼저 같은 배포 ID를 새 버전으로 업데이트한다. 초기화 전에는 기존 저장 경로를 계속 사용한다.
3. `setupAnnualQuoteOrderLedgers()`를 1회 실행한다. 현재 연도의 견적·주문 파일 및 월 탭을 준비하고 기존 견적 위치를 검증한 후 마지막 단계에서 새 저장 모드를 활성화한다. 파일은 **배포 소유자의 Google Drive**에 생성된다. 실행 결과의 `ready: true`, `storage: annual-v1`, `quoteFileId`, `orderFileId`를 확인한다.
4. 수정된 PC 프로그램으로 연결 후 동기화한다. 연결파일·URL·기기토큰을 새로 발급할 필요는 없다. 공개 정보 응답의 `ledgerStorage`가 `annual-v1`이어야 한다.
5. 운영 고객이 아닌 별도 테스트 견적으로 접수 → 견적확정 → 발송완료 → 입금확인 → 배송완료를 점검한다. 초기화·모의 테스트는 실제 입금 사실을 확인하는 기능이 아니다.

초기화 재실행은 동일 연도의 파일을 추가 생성하지 않는다. 실행 중 실패하면 오류를 해결하고 같은 함수를 재실행한다. 파일 생성 응답만 유실되어 Drive 검색이 아직 파일을 찾지 못하면 새로 만들지 않고 중단한다. 소유자가 확인한 파일을 `recoverAnnualLedgerFile('quote' 또는 'order', '2026', '파일ID')`로 연결할 수 있으며, 생성 토큰이 일치하는 파일만 허용한다.

## 기존 자료 보존과 내부 메타데이터

기존 견적·주문은 **자동으로 이동하거나 지우지 않는다**. 이미 저장된 원래 시트에서 계속 읽고 수정한다. 초기화 이후 새 견적/새 입금 주문부터 연도별 파일에 기록한다. 과거 전체 자료를 새 파일로 옮기는 일괄 이관은 이번 범위에 포함하지 않는다. 입금 전 상태로 등록된 구버전 Android 주문도 기존 저장소의 호환 경로를 유지한다.

기존 관리 파일에는 연결정보·이벤트 이력과 최소 메타데이터만 추가한다.
- `연도별장부파일`: 파일 종류, 연도, ID, 생성토큰, 생성상태.
- `연도견적색인`: 기존 방식의 견적 위치·상태 메타데이터. 고객정보를 복사한 장부가 아니다.
- `주문견적연결`: 견적 식별 해시와 주문번호. 완료·취소 후에도 같은 견적의 중복 전환을 방지한다.

구버전 월별 저장소에서 단일 저장소로 전환했던 경우에도, 오래된 사본이 아닌 현재 활성 자료를 기준으로 새 색인을 준비한다. 기존 보관기간·개인정보 삭제 정책은 변경하지 않으며, 종료된 주문의 익명 판매 집계와 보관기간이 지난 개인정보는 구분한다. 연도별 파일·월 탭을 직접 삭제하거나 내부 식별/상태 컬럼을 임의 편집하지 않는다. 일반적인 행 정렬은 지원한다.

## 로컬 저장·재시도

입금확인시각, 주문 확정본, 전송 대기를 로컬 DB에 저장한 뒤 네트워크를 시도한다. 인터넷이 끊기면 로컬 상태와 전송 대기를 유지하고 다음 동기화에서 같은 이벤트를 재전송한다. 서버 저장 후 응답만 유실돼도 주문이 중복되지 않는다. 같은 견적을 다른 PC에서 동시에 전환하면 서버가 중복을 거부하며 기존 충돌 화면에서 서버 주문을 채택할 수 있다.

입금 이후 주문 수정은 저장했던 버전을 검사한다. 다른 기기의 최신 수정이나 완료 기록을 오래된 로컬 화면으로 덮어쓰지 않는다. 견적 내용의 후속 수정은 이미 생성된 주문 확정본에 자동 반영되지 않는다.

## 검증 명령

```sh
node --test server/quote-requests/tests/*.test.cjs
PYTHONPATH=desktop:desktop/tests python -m unittest test_annual_ledgers -v
python -m compileall -q desktop/namufarm_desktop
```

서버 테스트에는 KST 월/연도 경계, 지연 업로드, 월 탭·연도 파일 생성, 행 정렬, 이벤트 재시도, 응답 유실, 버전 충돌, 중복 견적 전환, 기존 자료 보존, 부분 초기화 복구, 개인정보 만료가 포함된다. PC 통합 테스트는 실제 서비스/보관함 코드와 모의 Sheets에서 실행한 실제 Apps Script 코드를 연결한다. 실제 Google 계정/운영 데이터는 사용하지 않는다.

GUI·Windows 패키지 전체 검증은 Qt가 설치된 기존 CI 환경에서 별도로 수행한다. 이 문서의 모의 검증은 운영 Apps Script 배포와 실계정 점검을 대신하지 않는다.
