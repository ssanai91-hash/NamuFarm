# 만료 견적 정리 · 수동 운영 절차

2026-11-17, 4단계 구현. **코드 반영과 운영 적용은 별개다.** 빌드·시험·운영 데이터 정리·배포는 이번 작업에서 실행하지 않았다.

## 적용 순서

1. 기존 Apps Script 프로젝트에 `QuoteCompaction.gs`와 함께 변경된 `Code.gs`, `SecureCommerce.gs`, `TwoTabQuotes.gs`를 반영하고 **기존 웹 앱 배포를 새 버전으로 갱신**한다. 프로젝트·배포 ID·URL·인증을 새로 만들지 않는다. 자동 배포/새 트리거는 추가하지 않는다.
2. 서비스 정보의 `quoteSyncVersion:2`, `quoteStateBatchSize:50`을 확인한다. v2는 기존 annual-two-tabs에서만 지원한다. 레거시/월별 저장 형식을 임의 전환하지 않는다.
3. Android **1.1.45(48)**와 나피 **0.5.32**를 사용자가 빌드·업데이트한다. Android는 기존 패키지·고정 인증서로 업데이트하고 앱을 삭제하지 않는다. Android v2는 서버 미배포 시 기존 자료를 유지하며 배포 필요 메시지를 표시한다. PC는 서비스 정보로 v2를 협상하며 미지원 서버에는 기존 수신 경로를 사용한다.
4. 사용자 확인: 빈 목록, 10,000건 초과 유효 견적, 여러 차례 이어받기, 중간 종료/네트워크 실패, 오래 오프라인 후 재동기화, 자연 만료/관리자 삭제 구분, 읽음 표시, 확정·발송·초안·전송 대기, 기존 주문 수정과 견적-주문 연결을 확인한다. 운영 장부에 새 시험 주문을 만드는 것은 별도 판단 사항이다.
5. **실제 물리 정리는 기본 꺼짐이다.** 아래 소유자 계획·백업·활성화 절차를 따로 거친다. 클라이언트를 갱신하고 확인하기 전에는 켜지 않는다.

## 소유자 계획과 활성화

Apps Script 편집기 소유자 실행만 지원한다. 웹 API·클라이언트·공개 접수에서는 활성화/삭제할 수 없다. `purgeExpiredCustomerData`의 기존 만료 처리·설치 트리거는 유지되고, 새 물리 삭제를 자동 호출하지 않는다.

- `planExpiredQuoteCompaction()`을 실행해 연도/탭별 expired(정리 가능 만료), blank(업무 행 사이 빈칸), active, skipped, unusedGridRows와 planId를 확인한다. unusedGridRows는 마지막 값 행 뒤의 그리드 수이며 안전성 전수 판정 완료 수가 아니다. 실제 삭제 직전에 행 전체를 다시 확인한다. 계획 함수는 시트/색인/트리거를 생성하거나 업무 자료를 바꾸지 않는다.
- 기존 소유자 백업 절차로 **견적 연도 파일과 운영 관리 장부(색인·카운터/연결 포함)**를 보관한다. 서버 Script Properties의 LAST_SEQUENCE·일별 접수번호 카운터·주문 연결을 낮추거나 초기화하지 않는다. 백업 원문을 저장소/로그로 복사하지 않는다.
- 새 계획의 planId를 사용해 편집기의 임시 소유자 래퍼에서 `enableExpiredQuoteCompaction('계획의 64자리 planId')`를 호출한다. 편집기 Run은 인자를 전달하지 않으므로 래퍼가 필요하다. 예:

```javascript
function ownerEnableQuoteCompaction() {
  return enableExpiredQuoteCompaction('여기에_방금_확인한_planId');
}
```

- 활성화는 `QUOTE_COMPACTION_ENABLED=1`만 저장한다. 업무 행을 즉시 지우지 않는다. 이 래퍼/실제 planId는 저장소에 커밋하지 않는다.
- `compactExpiredQuotes()`를 **수동** 실행한다. 한 번에 삭제 최대 40행, 처리 예산 45초이며 초기 장부 검사/Google 호출 자체 시간은 별도 영향을 줄 수 있다. 반환값 removed/skipped를 확인한다. `morePossible:true`는 다음 계획 확인을 요청하는 힌트이며 남은 건수의 정확한 계산 결과가 아니다.
- `planExpiredQuoteCompaction()`으로 결과를 다시 보고 필요할 때만 다음 소량 작업을 실행한다. 한 건씩 안전하게 지우며 연속 대량 삭제로 최적화하지 않았다. 구역/행 번호를 영속 예약하지 않고 매번 UUID로 다시 찾는다.
- 마치거나 이상이 있으면 `disableExpiredQuoteCompaction()`을 실행한다. 기존 hourly 트리거를 바꾸지 않으며 다음 자동 실행을 예약하지 않는다.

## 색인·물리 삭제·복구

현재 견적 두 탭/18열과 주문 월별 탭/20열은 그대로다. 내부 `견적종료색인`은 기존 운영 관리 장부에만 생성된다. 스키마는 [QUOTE_ORDER_SHEET_SCHEMA.md](QUOTE_ORDER_SHEET_SCHEMA.md)에 정의했다.

ScriptLock 아래 종료 행을 색인에 먼저 저장·재조회해 VERIFIED를 확인한다. 현재 UUID·원문 지문·접수번호·시각·순번을 재확인하고 나서 실제 행을 삭제한다. 검증 실패는 원본 삭제를 중단한다. 삭제 후 REMOVED를 확인한다. 삭제 직후 중단돼 VERIFIED만 남아도 호환 읽기는 색인에서 종료 표식을 복원한다. VERIFIED가 반드시 미삭제 원본이 있다는 뜻은 아니다.

확정 이동의 중복 사본은 검증된 확정 행과 지문이 같을 때만 처리한다. 안전하지 않은 사본이 있으면 원본도 남긴다. 알려진 업무 탭의 빈 행/미사용 그리드 꼬리도 소량 줄이며 헤더와 최소 입력 행은 보존한다. 시트 보호·필터·차트·도형·이미지·이름 범위·밴딩·조건부서식, 병합/행 그룹, 후보 행의 값/수식/메모/유효성 검사 등 판단하기 어려운 구조는 보수적으로 건너뛴다. A:R 밖 자료도 확인한다. 다른 메모 탭을 정리하지 않는다.

같은 UUID+최초 지문 접수 재시도는 색인의 기존 접수번호를 돌려준다. 다른 지문은 CONFLICT다. 판매번호·주문견적연결·금융/주문/문의 이력은 삭제 대상이 아니다. 과거 만료로 없어진 가격·입금 증거를 만들지 않는다. 기존 주문 연결의 같은 번호 재시도/상태 갱신은 종료 색인을 참조하되 만료 견적을 다시 열지 않는다.

## v2 수신 계약

같은 인증 endpoint에서 `quoteSyncVersion:2`를 요청한다. `snapshot_requests` 또는 `list_requests`의 snapshot=true는 유효 견적만, snapshot=false는 변경과 최근 종료 표식을 반환한다. `fromSequence`는 세션 최초 커서, `afterSequence`는 현재 페이지 커서다. 전체는 fromSequence=0이다.

모든 페이지는 quoteSyncVersion=2, schemaEpoch=1, scope=active/changes, requiresSnapshot, snapshotId, total, watermark, minAvailableSequence를 포함한다. 페이지는 최대 100건이며 UUID/순번 중복·형식·날짜·토큰·총건수를 확인한다. total은 선택한 범위의 건수다. 90일 이전 종료 표식이 필요한 커서는 requiresSnapshot으로 전체 재수신한다. 90일은 고객 원문 보관 30일을 연장하지 않는다. 종료 색인의 식별/멱등 근거는 삭제하지 않는다.

`quote_request_states`는 requestIds 최대 50개를 인증 조회한다. 응답은 UUID/state/sequence만 포함하며 active/expired/admin_deleted/unknown을 구분한다. 로컬 확정/발송/작성 중/대기 기록의 웹 UUID와 요청 캐시를 확인한다. 단순 누락·unknown·자연 만료는 로컬 확정·초안·발송 증거를 지우지 않는다. 관리자 삭제는 근거와 원본을 먼저 보관하며 미완료 작업과 충돌하면 현재 자료·작업·삭제 journal을 유지하고 성공/커서 갱신을 보류한다. 자동 재발송하지 않는다.

v1 응답은 색인에서 최소 종료 표식을 재구성해 기존 의미를 유지한다. 구 앱/PC의 누적 상한을 없애 주지는 않으므로 갱신이 필요하다.

## 임시 수신과 커서

- Android: noBackupFilesDir의 독립 SQLite 수신 캐시. 업무 Room DB 3개의 이름/버전/테이블 불변. 20페이지 또는 약 60초 단위로 멈춰 **이어받기**를 안내한다. 상태 확인도 50개씩 최대 20배치 단위로 이어간다. 완료된 수신만 Room 트랜잭션으로 반영하고 NamuFarmPrefs에 cache 식별 지문+서버 watermark를 commit한다. Room 반영 뒤 checkpoint 저장 전 종료되면 전체를 다시 받아 안전하게 복구한다. 커서가 MAX(sequence)에 의존하지 않아 빈 목록도 진행을 유지한다. 수동 백업에 포함되는 prefs와 요청 캐시 지문을 대조한다.
- PC: 보관함 옆 `.quote-receive-v2.tmp` SQLite 파일의 고객 payload/메타를 기존 vault 암호로 보호한다. 기존 vault 스키마를 바꾸지 않는다. 페이지를 디스크에서 순차 반영하고 요청 캐시+watermark는 기존 vault 트랜잭션에 같이 저장한다. 완료 전 엑셀 사본을 교체하지 않는다. v2에서는 단순 목록 부재로 확정견적을 제외하지 않고 웹 초안의 기존 30일 자동 정리도 적용하지 않는다. 판매 페이지의 기존 상한/처리 방식은 이번 대상이 아니다.
- 두 클라이언트 모두 임시 파일의 고객 원문은 일반 백업과 업무 조회에 섞지 않는다. 완료/형식 오류/토큰 변경 때 비우며, 1시간 지난 세션은 시작/다음 수신 때 폐기한다. 일시중단·네트워크 실패 후 서버 토큰이 같으면 이어받는다. 저장 공간이 32MiB 이하이면 기존 자료를 유지하며 중단한다. 공간 확보 후 재시도한다.
- 10,000건/100페이지를 전체 건수의 영구 제한으로 쓰지 않는다. 다만 한 번의 동기화 호출로 전량 처리를 보장하지 않는다. 자주 바뀌는 snapshot은 BUSY로 재시작할 수 있고, 서버는 장부/종료 색인 메타를 스캔하므로 Google 실행시간·시트 용량과 로컬 공간 제약은 남는다.

## 이번 범위의 적용 상태

코드/문서만 구현했다. 운영 서버 재배포, 사용자 기기 업데이트, 물리 정리 계획 실행·백업·활성화·삭제는 미실행이다. 홈페이지 게시 없음. 5단계 P0 리뷰 기준과 6단계 clasp 연결은 다음 승인 대기다.
