# 견적 접수 월별 저장 · 운영 전환 안내

이 변경은 **접수 서버 코드**다. 저장소 커밋만으로 운영 Apps Script가 배포되거나 고객 데이터가 이동하지 않는다. 홈페이지 디자인, PC·Android 기능, 판매 원장 형식은 변경하지 않는다. 홈페이지 접수는 견적 상담 요청이며 주문·결제 확정이 아니다.

## 1. 기존 구조와 변경 범위

기존 `SPREADSHEET_ID`의 `웹견적요청` 한 시트에 접수, 중복 검사, 조회, 알림, 30일 삭제가 모두 연결되어 있었다. 시트만 월별로 나누면 과거 UUID 재전송이 중복 접수되고, 앱의 전역 커서와 이전 달 파기가 끊길 수 있다.

확인한 경로와 변경은 다음과 같다.

| 경로 | 이번 변경 |
|---|---|
| `SecureCommerce.gs`의 `submitEncryptedRequest_` | 설정 후에는 전체 색인으로 UUID·해시를 확인하고 선택된 월/일에 저장 |
| `listEncryptedRequests_` | 전체 색인에서 순번을 정렬하고 여러 파일의 요청을 같은 응답 형식으로 결합 |
| `closeRequest_`, `closeLinkedRequest_`, `purgeExpiredCustomerData` | 월/일 위치에 관계없이 종료하고 새 변경 순번으로 tombstone 전달 |
| `Code.gs`의 `dispatchNotifications_` | 색인으로 실제 행을 찾아 outbox 처리. FCM 호출은 잠금 밖에서 수행 |
| `sheet_`, 접수번호 초기 설정, 기존 평문 암호화 이관 | 기존 시트를 위한 경로 유지. 월별 복사 이관과 별개의 기능 |
| `MonthlyStorage.gs` | 월 파일 등록부·색인·실패 복구·월간현황·소유자 전환/복사 도구 신설 |
| `website/app/api/quote-requests/route.ts` | 암호화 전송 및 접수번호 검증 계약이 같아서 변경 불필요 |
| 기존 판매 기록/판매 변경 이력 | 저장 위치와 API, 5년 보관 처리 유지. 연결된 견적 종료만 새 저장 계층으로 연결 |

세 `.gs` 파일과 manifest는 **같이 적용**한다. 기본 모드는 여전히 기존 저장 방식이다. 소유자가 아래 설정 함수를 실행하기 전에는 월별 쓰기가 켜지지 않는다.

## 2. 최종 저장 구조

| 위치 | 내용 |
|---|---|
| 기존 관리 파일 / `견적월별파일` | 월, 실제 파일 ID, 생성 토큰, 생성 상태, 생성 시각 |
| 기존 관리 파일 / `전체견적색인` | UUID, 원본 위치, 접수일/시각/번호, HMAC 내용 검증 값, 최신 변경 순번, 저장 단계, 이관 메타데이터, 상태 |
| 기존 관리 파일 / `웹견적요청` | 이전 자료를 그대로 유지. 색인이 이 위치를 참조 |
| `나무팜_견적요청_2026-10` / `2026-10-07` | 접수 한 건당 한 행. 접수 있는 날짜만 생성 |
| 같은 월 파일 / `월간현황` | 날짜, 접수 건수, 신규 건수, 보관 종료 건수, 집계 갱신 시각 |
| `나무팜_견적요청_2026-11` | 다음 달의 날짜별 시트와 월간현황 |

날짜는 서버 접수 시각의 **Asia/Seoul** 날짜로 정한다. UTC 원본 시각과 한국 표시 시각을 모두 유지한다. 새 파일은 실행 소유자의 Drive에 생성하며 공유 권한·공유 폴더를 자동 확대하지 않는다. 파일명이 바뀌어도 등록한 파일 ID로 연다. 생성 직후 Google이 기본 빈 탭을 제공하는 경우 이를 삭제하지 않는다.

날짜별 행은 기존 A:R 18열 구조를 유지한다. A는 UUID, B는 최신 변경 순번, C는 UTC 접수 시각, D:I는 빈 칸, J:O는 상태·알림·내용 검증 메타데이터, P는 암호화 본문 또는 종료 표식, Q:R은 접수번호·한국 시각이다. 전화번호, 성함, 품목, 규격, 수량, 공식 견적서 요청 여부/수신인/전달 방법은 기존 암호문 안에 보존한다. 서버에 판매자 개인키를 추가하지 않는다.

색인에는 고객정보나 암호화 본문을 복사하지 않는다. `최초예약행`은 아직 없는 행을 위한 쓰기 자리일 뿐이다. 저장된 행은 항상 UUID로 찾는다. 정렬로 예약 자리가 다른 UUID에 점유되면 새 빈 자리를 예약하며 기존 행을 덮어쓰지 않는다. 시트의 초기 행 수를 넘으면 필요한 행을 확장한다.

월간현황은 서버가 사용하는 `신규`와 `보관종료` 상태를 집계한다. 상담 중/견적 발송 같은 새로운 업무 상태는 이번에 추가하지 않는다. 이관하지 않은 기존 자료는 아직 월 파일의 집계 대상이 아니다. 집계 갱신 실패는 접수를 취소하지 않으며 유지보수 트리거가 다시 계산한다.

## 3. 접수·복구 프로토콜

여러 스프레드시트에 걸친 원자적 트랜잭션을 가정하지 않는다. ScriptLock으로 같은 Apps Script 프로젝트의 접수·조회·파기·유지보수·이관을 직렬화한다. 같은 관리 파일을 쓰는 두 번째 Apps Script 프로젝트를 함께 운영하면 이 잠금이 공유되지 않으므로 배포 전 쓰기 주체를 하나로 통일한다.

### 요청 색인 상태

| 단계 | 영속 상태 | 실패 시 동작 |
|---|---|---|
| `PREPARED` | 접수번호/시각/UUID/해시/목적지를 색인에 예약, 순번은 0 | 데이터가 없으면 같은 UUID의 재전송을 기다린다. 내용이 다르면 충돌 |
| 후보 데이터 기록 | 날짜 시트에 암호문과 순번 0을 저장 | 응답이 끊겨도 UUID로 찾는다. 후보 행은 아직 조회에 공개하지 않는다 |
| `COMMITTING` | 후보 행 확인 후 전역 변경 순번을 예약하고 색인에 기록 | 같은 순번으로 실제 데이터 행을 마무리한다. 실패하면 조회 페이지도 성공 처리하지 않는다 |
| `COMMITTED` | 데이터 행과 색인을 flush 후 각각 다시 읽어 확인 | 이때만 접수 성공/동기화 대상이 된다 |
| `DISPOSING` | 새 변경 순번을 갖는 보관 종료 의도 | 원본과 관리 중인 이관 사본을 모두 지운 뒤 `COMMITTED` |
| `MIGRATING` | 원본·목적지 ID와 예약 위치를 기록 | 행 전체를 동일하게 복사·확인하고 색인의 위치를 바꾼다 |

모든 접수, 목록 조회, 유지보수는 미완료 전환을 먼저 복구한다. `PREPARED`에 데이터가 없는 것만으로 다른 정상 요청의 진행을 막지는 않는다. 이 예약은 나중에 데이터가 생긴 때의 **새 순번**을 받는다. 따라서 앱이 이미 받은 커서 아래로 늦게 요청이 나타나지 않는다.

예약 자체의 첫 쓰기 전에 실패했다면 아직 확정된 최초 접수는 없으며 번호에 공백이 생길 수 있다. 예약이 저장된 뒤에는 다음 날/다음 달 재시도라도 최초 접수번호·접수일시·목적지를 유지한다. 같은 UUID의 내용 검증 값이 다르면 기존 `CONFLICT`를 반환한다. 저장 실패 또는 결과 불확실은 성공으로 반환하지 않는다. 캐시 실패 후에도 재전송으로 이미 저장된 접수를 찾는다.

색인 예약을 확인하기 전에 데이터를 쓰지 않는다. 따라서 정상 프로토콜의 ‘데이터만 저장’은 **PREPARED 예약은 있고 최종 색인이 미완료인 상태**로 복구한다. 수동으로 색인 행을 삭제한 별도 손상까지 자동 추측하여 복원하지는 않는다. 감사에서 중단하고 UUID·원래 메타데이터를 대조하여 복구해야 한다.

알림은 접수 확정 뒤 시도한다. 실패하면 기존 PENDING/재시도 outbox가 남으며 접수 성공을 취소하지 않는다. 알림을 보내거나 재시도해도 요청 변경 순번은 증가하지 않는다.

### 월 파일 생성 상태

1. 월 등록부에 고유 생성 토큰을 `RESERVED`로 저장하고 확인한다.
2. `CREATING`을 저장한 뒤 Drive API로 Google 스프레드시트를 생성한다. 파일의 `appProperties`에 관리 파일 식별 해시와 생성 토큰을 함께 기록한다.
3. 실제 파일 ID를 저장하고 한국 시간대/월간현황을 준비한 뒤 `READY`로 바꾼다.
4. 생성 응답 유실 시 이름 검색이 아닌 **생성 토큰 검색**으로 같은 파일을 연결한다.
5. `CREATING`인데 검색 결과가 없거나 둘 이상이면 자동 재생성하지 않는다. 실제 생성 실패와 아직 보이지 않는 생성 결과를 구별할 수 없으므로 `NOT_READY`로 멈춘다.

Google Sheets 같은 Workspace 파일 생성에는 사전 발급한 Drive ID를 사용할 수 없으므로, 토큰을 함께 생성하고 불확실할 때 중단하는 방식을 사용했다. 이 제한 때문에 ‘모든 Google 장애에서 무조건 자동 복구’는 보장하지 않는다.

## 4. PC·Android 조회와 보관 종료

- 공개 서비스 버전은 **4**, `requestDeletionSync: true`, 보관일은 **30일**이다. 기존 홈페이지 계약을 바꾸지 않는다.
- `list_requests`의 `afterSequence`는 0 이상의 정수이며 전체 기간의 변경 순번이다. 요청 UUID, sequence, createdAt, expiresAt, 접수번호·한국 시각, encryptedRequest 또는 expired 필드를 유지한다.
- 색인의 최신 순번을 기준으로 오름차순 최대 100건과 `hasMore`를 반환한다. 파일마다 커서를 따로 만들지 않는다. 앱은 기존대로 페이지 반영이 완료된 최대 순번에서 재개한다.
- `LAST_SEQUENCE`는 모든 월/기존 자료를 통틀어 증가한다. 실패로 빈 번호가 생길 수 있으므로 연속 번호가 있다는 가정은 하지 않는다. 판매 순번 `SALE_SEQUENCE`는 기존대로 별도다.
- 조기 종료, 구매 연결 종료, 30일 보관 종료는 새 순번의 `expired: true` 변경을 만든다. 반복 종료는 순번을 계속 올리지 않는다.
- `purgeExpiredCustomerData`는 현재 달이 아닌 **전체 색인**을 확인한다. 지난달/작년 자료와 복사 이관 후 남긴 기존 시트 사본도 파기한다.
- 만료된 자료는 조회 시 암호문을 반환하지 않는다. 실제 셀 파기는 기존 5분 주기 트리거가 담당한다. 트리거 실패/지연을 감시해야 하며 실행 주기를 정확한 삭제 시각으로 보장하지 않는다.
- 종료 뒤에는 암호문을 `{"expired":true}`로 바꾸고 outbox를 중지한다. UUID·접수번호·최종 순번·내용 검증 값 등 중복 방지/삭제 동기화 메타데이터와 고객정보 없는 건수는 남긴다. 색인 tombstone을 임의 삭제하지 않는다.

## 5. 초기 설정과 운영 배포 순서

### 사전 점검 — 먼저 격리된 Google 테스트 환경에서

1. 별도 Apps Script 프로젝트와 빈 관리 스프레드시트를 만들고 **테스트용 키/비밀값/기기 연결**만 사용한다. 운영 `SPREADSHEET_ID`, 운영 고객 원문, 운영 알림 기기를 테스트에 연결하지 않는다.
2. `Code.gs`, `SecureCommerce.gs`, `MonthlyStorage.gs`, `appsscript.json`을 함께 반영한다. Apps Script 고급 서비스의 **Drive API v3**를 활성화한다. 표준 Google Cloud 프로젝트를 연결했다면 해당 프로젝트에서도 Drive API 활성화를 확인한다. manifest의 새 `drive.file` 권한으로 실행 소유자가 재승인한다.
3. 기존 설치 순서대로 `SPREADSHEET_ID`, `WEB_SECRET` 등을 설정하고 `setupQuoteRequests()` 실행, 기존 PC/앱 경로의 암호화 키 등록을 마쳐 GET `encryptionReady: true`를 확인한다. 이미 운영 중인 키/비밀값/연결 정보는 초기화하지 않는다.
4. `setupMonthlyQuoteStorage()`를 실행한다. 기존 암호화 자료의 색인을 제자리에서 만들고 유지보수 트리거를 추가한다. 기존 UUID, 접수번호, 시각, 암호문, 해시, 순번은 재발급하지 않는다. 쓰기 모드는 아직 `legacy`다.
5. `auditMonthlyQuoteStorage()`로 개수/예약/월 등록부를 검사한다. 이 함수는 **읽기 전용**이다. 미완료 전환은 `maintainMonthlyQuoteStorage()` 실행 후 다시 감사한다.
6. `enableMonthlyQuoteStorage()`를 실행한다. 선택적으로 `prepareQuoteMonth('2026-10')`로 실제 전환 월을 미리 준비한다. Apps Script 편집기의 인수 없는 실행 메뉴를 사용할 때는 임시 소유자용 wrapper 함수에서 인수를 전달한다. 날짜 시트는 아직 생성하지 않는다.
7. 격리된 테스트 배포에서 가상 고객 요청, 동시 호출, 동일 UUID 재전송, 잘못된 내용, 다중 페이지, 종료 후 두 기기의 동기화를 확인한다. 테스트 파일의 접근 권한, 한글 헤더/타입, 실제 실행 시간/할당량도 확인한다. 자정/월말은 테스트 시계 주입 또는 해당 경계 시험으로 검증하고 운영 시간을 변경하지 않는다.

### 운영 반영 — 별도 실행 단계

1. 운영 관리 파일 ID, 기존 행 수/UUID 수/최대 순번, 키 ID, 배포 버전, 트리거와 Script Properties 설정을 운영자가 안전하게 기록한다. 비밀값과 고객 원문을 로그나 Git에 남기지 않는다. 필요한 백업은 암호화·접근 제한·삭제 기한을 함께 정한다.
2. 짧은 점검 시간에 접수 진입을 제한하고 기존 버전의 진행 중 실행이 끝난 것을 확인한다. 같은 관리 파일을 쓰는 구 버전/별도 프로젝트가 계속 쓰지 않도록 한다. 저장소 위치·순번을 바꾸는 기간에는 수동 셀 편집을 하지 않는다.
3. 세 `.gs` 파일과 manifest를 같은 프로젝트에 반영하고 권한을 승인한다. 기존 웹 앱 배포를 새 버전으로 갱신해 **동일한 `/exec` URL**을 유지한다. 이때 READY/MODE를 임의로 미리 설정하지 않는다.
4. `setupMonthlyQuoteStorage()` → `auditMonthlyQuoteStorage()`를 실행한다. 감사의 committed 수를 기존 UUID 수와 대조하고 기존 시트 내용이 그대로인지 확인한다. 새 월 생성 전까지 기존 모드의 조회도 유지된다.
5. 실제 전환 월을 `prepareQuoteMonth`로 준비하여 Drive 생성/등록 권한을 확인한다. `enableMonthlyQuoteStorage()`를 실행한다. `QUOTE_STORAGE_READY=1`, `QUOTE_STORAGE_MODE=monthly-v1`이 되었는지 확인한다.
6. GET 응답의 기존 v4 암호화/보관/접수번호 계약, 트리거 상태, 감사 결과를 읽기 점검하고 접수를 다시 연다. 운영 시트에 가짜 요청을 보내지 않는다. 다음 실제 고객 접수는 권한 있는 운영자가 접수번호/색인/일자 위치/기존 앱 수신 여부를 대조한다.
7. 최초 하루와 월 전환 때 Apps Script 실패 실행, 미완료 저장 단계, 월간현황 갱신, 이전 월 삭제 처리를 확인한다.

| 설정/함수 | 역할 |
|---|---|
| 기존 `SPREADSHEET_ID` | 월 등록부·색인을 보관할 관리 파일. 월 파일 ID로 바꾸지 않음 |
| `QUOTE_STORAGE_READY` | 설정 함수가 성공하면 `1`. 운영 중 수동으로 지우지 않음 |
| `QUOTE_STORAGE_MODE` | `monthly-v1` 또는 `legacy`. 신규 쓰기 위치만 선택 |
| `maintainMonthlyQuoteStorage` | 5분 유지보수: 중간 전환 복구, 월 등록부 연결, 집계 재생성 |
| `purgeExpiredCustomerData` | 기존 5분 개인정보 파기 트리거. 월별 유지보수와 별개로 계속 필요 |
| `dispatchQuoteNotifications` | 기존 분 단위 알림 재시도 |

## 6. 선택적 기존 자료 이관

전환만으로는 기존 행을 이동하거나 삭제하지 않는다. 색인이 기존 `웹견적요청`을 직접 가리키므로 과거 요청은 계속 조회·중복 검사·파기된다. **기본 권장은 이 상태로 전환하고 안정화한 다음 필요한 자료만 복사 이관하는 것**이다.

별도 승인된 이관 창구에서 다음을 실행한다.

1. 감사 성공과 파기 트리거 정상 여부를 먼저 확인한다. 운영 원본·색인의 UUID별 접수번호/시각/해시/암호문/순번 비교 자료를 권한 있는 환경에서 준비한다.
2. 소유자 함수 `copyLegacyQuotesToMonthly(10)`을 실행한다. 인수는 1~20이며 최초에는 소량을 선택한다. API 액션으로 외부에 노출되지 않는다.
3. 각 원본 행 전체를 원래 접수일의 월/일 시트에 복사한다. 본문을 재암호화하거나 식별값을 재발급하지 않는다. 대상 확인 후에만 색인이 대상을 참조한다. 원본 행은 남기며 `기존시트사본=true`로 파기 관리에 포함한다.
4. 중단되면 유지보수 또는 같은 이관 함수를 재실행한다. UUID로 이미 복사된 행을 찾아 내용 전체를 비교한 뒤 이어간다. 일치하지 않으면 자동 덮어쓰지 않고 충돌로 중단한다.
5. 감사로 누락·예상 밖 중복·본문 불일치를 확인하고, 이관 전후 UUID 집합과 원래 접수번호/시각/해시/암호문/최신 순번을 대조한다. 앱에 같은 요청이 새 건으로 생기지 않는지 확인한다. 이관 후 알림 상태나 파기로 정상 변경된 메타데이터는 비교 시 구분한다.
6. 필요한 범위까지 반복한다. 이 구현은 원본 행 삭제 도구를 제공하지 않는다. 원본을 수동 삭제하면 관리 중인 사본 확인/파기가 실패할 수 있으므로 별도 후속 제거 설계 없이 삭제하지 않는다.

## 7. 장애 복구와 되돌리기

| 관찰된 상태 | 복구 방법 |
|---|---|
| 접수 응답 실패, `PREPARED`에 데이터 없음 | 고객의 같은 UUID·같은 내용 재시도. 새 UUID로 중복 접수하지 않음 |
| 데이터 있음, `PREPARED`/`COMMITTING` | 저장소 권한/쿼터 회복 후 재시도 또는 유지보수. 확인 완료 전 조회 커서도 성공으로 내보내지 않음 |
| `DISPOSING`/`MIGRATING` | 저장소 접근 회복 후 유지보수. 미완료 이관의 원본과 대상은 지우지 않음 |
| `CREATING`, 토큰 검색에서 파일 한 개 발견 | 같은 요청 또는 유지보수가 해당 ID를 등록하고 마무리 |
| 파일 ID는 확실한데 검색 반영이 지연됨 | 소유자 `recoverQuoteMonthFile('2026-10','실제ID')`. 토큰·관리 파일 해시·파일 종류가 일치할 때만 연결 |
| `CREATING`, 파일이 보이지 않음 | 생성/권한 오류와 실행 기록 조사. 검색 결과 없음만으로 재생성/토큰 초기화하지 않음. 필요하면 아래 기존 쓰기 모드로 우회 |
| 생성 호출이 실행되기 전에 중단된 것이 명확히 확인됨 | 접수/유지보수를 잠시 정지하고 소유자가 해당 월의 빈 ID·동일 토큰을 유지한 채 상태를 `RESERVED`로 되돌린 후 재시도 가능. 생성 여부를 확인할 수 없으면 이 조치를 하지 않음 |
| 중복 토큰 파일, 삭제된 원본, 색인 손상 | 자동 추측 복구하지 않음. 접근 제한된 원본/백업과 UUID·해시·접수번호·순번을 대조하고 연결을 복원한 뒤 감사 |
| 월간현황만 오래됨 | 유지보수 재실행. 집계 실패는 확정된 접수나 앱 커서를 되돌리지 않음 |

월별 신규 쓰기를 멈추려면 **새 코드를 유지한 상태에서** `useLegacyQuoteWrites()`를 실행한다. 이후 새 접수는 기존 시트에 쓰되 색인은 계속 갱신하고 이미 생긴 월별 자료도 함께 읽고 파기한다. 파일 생성이 불확실한 빈 월 등록부는 이 우회만 허용하며 원본이 있는 요청의 손상을 숨기지는 않는다. 미완료 데이터 전환은 먼저 복구해야 한다.

새 월별 자료가 생긴 뒤 구 코드를 재배포하거나 `QUOTE_STORAGE_READY`를 지우는 방법으로 되돌리면 월별 자료가 조회·파기에서 빠진다. 이는 지원하는 복구 방식이 아니다. 운영 전체를 과거 백업으로 덮어쓰는 것도 기존 고객 재시도·앱 커서와 충돌하므로, 장애 동안의 신규 UUID/순번까지 대조하는 별도 복원 절차가 필요하다.

## 8. 자동 테스트와 미확인 범위

```bash
node --test server/quote-requests/tests/*.test.cjs
node --test website/tests/*.test.mjs
```

구현 검증 시 서버 **108개**(기존 52개 + 월별 56개), 최신 홈페이지 **19개**가 통과했다. 서버 테스트는 메모리 기반 다중 파일/시트와 실제 Node 암호 연산을 사용한다. Google 서비스·네트워크는 호출하지 않으며 가상 개인정보만 쓴다.

| 요구 사례 | 자동 검증 내용 |
|---|---|
| 월/일 자동 생성 | 접수 있는 날만 생성, 파일명 변경 후에도 ID 사용, 시트 행 수 확장 |
| 동시 요청 | 잠금 중 다른 접수를 끼워 넣어 BUSY·재시도·파일/시트/접수번호/UUID 유일성 검증 |
| 한국시간 경계 | UTC 14:59:59 → 15:00:00, 월말·연말, 날짜별 번호와 전역 순번 |
| UUID 재전송/충돌 | 다음 달 재시도에도 최초 번호/시각/암호문 유지, 내용 변경 거절 |
| 중간 실패 | 색인 예약, 후보 행, COMMITTING, 실제 순번, COMMITTED 각각 적용 전/후 응답 유실과 재시도 |
| 파일 생성 실패 | 생성 응답 유실 시 토큰 연결, 불명 결과에서 재생성 금지, 정확한 ID 복구 |
| 페이지/커서 | 두 달 105건을 100+5로 조회, 빈 예약의 지연 복구가 이미 반환한 커서 뒤로 나타남 |
| 보관 종료 | 이전 달 30일 파기, 조기 종료, 각 저장 단계 실패, 반복 종료, 기존 사본 동시 파기 |
| 기존 호환 | 원본 불변의 색인 설치/재실행, 혼합 조회, 기존 쓰기 우회, 복사 이관 중단/복구 |
| 기존 기능 | 암호문·공식 견적서/전달 방법 보존, 구매 연계 파기/판매 원장 보존, 알림·집계·캐시 실패 분리 |

2026-10-07에는 별도 시험 파일·키로 실제 Drive/Sheets 접수, 중복·충돌, 기기 인증, 삭제 동기화, 월 파일 생성·감사를 검증하고 운영 전환했다. 실환경에서 확인한 일반 텍스트 셀의 boolean 문자열 변환을 반영하여 사본 여부를 명시적으로 `"true"`/`"false"`로 저장하고 읽을 때 논리값으로 정규화한다. 기존 boolean 값도 읽으며 잘못된 값은 거절한다. 상세 결과와 남은 OAuth 게시 설정은 [운영 전환 기록](OPERATIONS_20261007.md)에 있다. 실제 병렬 부하, 색인 검색 지연 장애, API 한도, PC·Android 실기기 수신은 검증하지 않았다. 운영 시트에는 가짜 접수를 보내지 않았다.

현재 방식은 전체 색인의 메타데이터를 읽어 정렬하고 해당 페이지가 참조하는 날짜 시트만 연다. 잠금 안의 읽기 페이지에서는 날짜 시트를 한 번씩 읽어 UUID별로 묶으므로 같은 시트를 요청 건수만큼 다시 읽지 않는다. 정기 파기/알림과 쓰기 경로는 대상 자료를 순회한다. 실제 예상 접수량의 격리 데이터로 실행 시간과 할당량을 측정한다. 규모가 커지면 쓰기 경로의 읽기 묶음/분할 유지보수를 추가하되 커서와 복구 순서의 의미를 유지해야 한다.

## 9. Excel 내보내기 후속 확장

실시간 원본은 Google 스프레드시트다. `.xlsx` 생성·배포는 이번 접수 경로에 넣지 않는다. 나중에 고객정보 없는 월간현황 내보내기를 우선 제공할 수 있다.

암호화 본문까지 내보내려면 별도 작업에서 일관된 확정 상태를 확인하고, 사본별 포함 UUID·만료 시각·위치·접근권한을 관리해야 한다. 서버에서 평문으로 풀어 쓰지 않는다. 관리되는 Drive 사본은 30일/조기 종료와 연결하여 삭제 또는 암호문 제거를 수행해야 한다. 이미 사용자가 내려받은 오프라인 파일은 서버가 회수하거나 원격 파기할 수 없으므로 자동 파기를 보장하면 안 된다. 해당 사본의 보관·삭제 책임과 방법을 먼저 정하거나 개인정보 없는 집계만 내보내는 정책을 선택한다.
