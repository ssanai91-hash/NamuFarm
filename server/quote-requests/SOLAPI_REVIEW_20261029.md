# SOLAPI 약관 개정과 나무팜 문자 검토

검토일: 2026-10-29 (한국시간). 기준: GitHub `main`의 `9701c8d5b81502928ce4c1ba70776946c7a7875a`.

## 결론

현재 기본 견적·입금·문의답변 문구는 고객이 요청한 범위의 회신 또는 거래 이행에 한정하면 거래성 안내로 판단된다. **실제 수신문구·요청 경위에 따라 달라지는 코드 기반 판단**이며, 운영 발송내역 전체에 대한 적법성 판정은 아니다. 할인·추가상품 권유를 섞거나 요청 없이 반복 권유하면 광고로 검토해야 한다.

메일 원문과 현재 공식 공지·개정 전문의 시행일은 **2026-11-28**이다. URL의 `20261123` 및 검색에 남은 과거 시행일과 구별한다. 개정은 광고 관련 기존 의무를 명확히 하고 불법스팸의 즉시 중단·서비스 거부·해지 조치를 정비한다. 계정 제한은 정상 거래 문자에도 영향을 줄 수 있다. 시행일 이후 계속 이용하려면 SOLAPI 계정에서 개정 약관 동의가 필요하다. 계정의 실제 동의 여부는 확인하지 않았다. [1][2]

## 문자별 분류와 발송 조건

| 유형 | 조건부 분류 | 발송 조건과 경계 |
| --- | --- | --- |
| 고객 요청 견적 | 거래성 | 특정 요청에 대한 회신. 요청 품목·가격·배송비·해당 견적의 계좌 안내에 한정. 미구매 고객 대상 반복 권유·다른 상품 홍보는 별도 광고 검토 |
| 주문 입금계좌 안내 | 거래성 | 실제 요청 견적·합의 주문의 결제에 필요한 내용. 불특정 고객에게 계좌와 구매 권유를 보내는 경우에는 적용 불가 |
| 입금 확인 | 거래성 | 실제 입금 확인 후 해당 주문·금액·준비 상황만 통지. PC 기본 문구는 입금 요청이 아니라 “입금 확인했습니다”이므로 실제 확인 전에 사용하면 안 됨 |
| 고객문의 답변 | 거래성 | 고객이 남긴 문의와 관련된 회신. 자유입력 답변에 판촉을 추가하면 광고 여부 재검토 |
| 계절별 묘목 관리 | 내용·관계별 판단 | 구매한 묘목의 약정상 필요한 사후관리만 제공하는 경우 예외 검토 가능. 일반 고객 명단 대상 정기 정보·재구매 유도·상품 추천은 광고로 준비. “관리 안내”라는 이름만으로 거래성이 되지 않음 |

KISA는 계약 전 특정 요청에 대한 1회성 정보, 거래 완성·확인 및 보증 등 필요한 정보를 광고 예외로 설명한다. 위 표는 그 기준을 현재 템플릿에 적용한 판단이다. 거래성 안내에 광고 수신 동의를 새로 강제하거나 `(광고)`·080을 일괄 삽입할 근거는 확인되지 않았다. 광고 수신거부를 거래상 필수 통지의 거부와 동일시하지 않되, 공급자가 이미 차단한 번호로 우회 발송해서는 안 된다. [3]

## 광고 발송을 시작하기 전에 필요한 기능

- 개인정보 처리 고지·동의와 구분된 **선택적 문자 광고성 정보 수신동의** 및 증빙: 번호, 매체, 문구 버전, 일시, 취득 경로, 철회 이력. 현재 문의의 `consent:true`, 견적의 `processingBasis:quote_request`, 문자 회신 선택은 광고 동의가 아니다. [4][5]
- 발송 직전 철회·수신거부 확인, 무료 080 등 실제 작동하는 거부 수단과 차단 목록 연동. 거부 뒤 광고 중단. 동의·거부·철회의 처리결과는 14일 이내 안내하고, 동의 여부 확인 안내는 2년마다 시행. [2][6]
- 본문 시작의 `(광고)`, 전송자 명칭·연락처, 무료 수신거부 방법. SOLAPI 기준상 제목이 있는 광고 메시지는 제목에도 `(광고)`가 필요하다. 현재 발송은 제목 없는 자동 SMS/LMS 판별이고 광고 전용 제목·거부 표시 기능이 없다. [2][7]
- 한국시간 21:00~08:00 광고는 별도 사전 동의 필요. 나무팜은 도입 시 주간 발송만 허용하는 편이 단순하다. 현재 시간 제한이 없는 거래성 경로를 광고 예약 발송에 재사용하지 않는다. [2]
- 기존 거래의 사전동의 예외는 직접 수집한 연락처, 거래 종료 후 6개월 이내, 실제 거래한 것과 동종 상품 등 요건이 필요하다. 단순 문의·견적 접수만으로 적용하지 않는다. 현재 코드에는 이를 검증하는 광고 발송 체계가 없다. [6]

위 기능은 미래 기능의 도입 조건이다. 이번 수정에서 광고 발송 기능이나 동의 기록을 만들어 기존 고객에게 동의가 있는 것으로 처리하지 않았다.

## 확인된 문제와 수정

1. **문의의 확정 거절을 결과 불명으로 저장**: 공급자가 명확히 거절해도 `unknown`에 갇혔다. 이제 `failed`로 저장하고 사유를 보존한다. 문의 완료로 처리하지 않으며, 같은 발송 ID 재호출은 전송하지 않는다. 시간초과는 계속 `unknown`으로 보호한다.
2. **견적·입금 거절 사유 유실**: `failedMessageList` 상태코드가 버려지고, 재조회에도 일반 거절만 나왔다. 안전한 상태코드·내부 고정 설명을 기록·재조회하고 PC에서 표시하도록 수정했다. 공급자 원문은 고객정보를 포함할 수 있어 기록하지 않는다.
3. **모순된 공급자 결과의 재발송 위험**: 실패 목록과 다른 접수/성공 결과가 섞이면 거절 확정 대신 `unknown`을 유지한다.
4. **차단 사유 설명 부족**: `1060`, `1061/2061/3061`, `1064/2064`, `1065/2065`, `2254`를 구별했다. 자동 재발송·발신번호 변경·다른 경로 우회는 추가하지 않았다. [8]

PC 버전은 저장소 기준에 따라 `0.5.9` → `0.5.10`. Android는 기존 `failed` 상태와 호환된다. Android의 문의 화면은 현재 일반 실패 라벨을 사용하고 상세 설명 표시는 추가하지 않았다. 기존에 저장된 `unknown`을 일괄 실패로 바꾸지 않았다. 과거 건은 SOLAPI 발송내역으로 확인해야 한다.

## 검증과 운영 반영

- 원본 서버 코드에서 추가한 핵심 회귀 테스트 2개가 각각 `unknown/failed` 오분류와 상태코드 유실로 실패하는 것을 재현했다.
- 수정 후 서버의 견적발송·고객문의 테스트 17개, PC 발송 연동 테스트 9개 통과. 중복 ID, 시간초과, 확정 거절, 혼합 응답, 개인정보 미기록, 응답 유실 후 조회 복구를 포함한다.
- 고객문의 단위 테스트의 기존 누락 의존성 `purgeQuoteDeliveries_`를 격리용 스텁으로 보완했다. 실제 발송기록 정리는 별도 견적발송 테스트에서 확인한다.
- 테스트는 격리된 가짜 장부·가짜 공급자만 사용했다. 실제 고객 문자·메일, 운영 API, 고객자료 변경, GitHub Actions를 실행하지 않았다. PC GUI 실행·설치파일 빌드·Android 컴파일은 수행하지 않았다.
- 운영 반영은 기존 Apps Script 프로젝트의 `SecureCommerce.gs`, `CustomerInquiries.gs`를 갱신하고 **기존 `/exec` 배포를 새 버전으로 재배포**해야 한다. 배포 URL·ID·Script Properties는 유지한다. 이번 작업은 GitHub 코드 커밋까지이며 운영 재배포는 하지 않았다.
- PC 상세 오류 표시는 `0.5.10` 코드로 업데이트해야 보인다. 이전 PC도 서버의 기본 발송 응답 구조와 호환된다.
- 시행 전 계정 소유자가 SOLAPI 공식 콘솔에서 개정 약관 동의와 등록 발신번호·계정 상태를 확인한다. 광고 기능은 동의·무료 거부·시간대·표시 체계를 갖추기 전 도입하지 않는다.
